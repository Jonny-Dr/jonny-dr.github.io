# LLM 模型、量化、QLoRA 与多卡推理：核心知识整理

> 本文将前后几轮关于 **Dense / MoE、INT4 量化、QLoRA、70B 模型显存、多卡推理、Tensor Parallelism、Pipeline Parallelism、NCCL、KV Cache、vLLM** 的内容统一整理。
>
> 目标不是堆概念，而是建立一条清晰的知识链：
>
> **模型结构 → 参数量 → 量化 → 显存 → 多卡 → TP → NCCL → KV Cache → LLM 服务部署**

---

## 1. Dense 模型与 MoE 模型

### 1.1 Dense：每次都用全部参数

**Dense Model（稠密模型）** 可以简单理解成：

> 每次处理一个 Token 时，模型中的主要参数都会参与计算。

例如一个 70B Dense 模型：

```text
70B Parameters
       ↓
每次推理
       ↓
大部分参数都参与计算
```

因此：

- 参数量大，模型容量大；
- 每次计算量通常也比较大；
- 模型结构比较直接；
- 部署和推理逻辑相对容易理解。

### 1.2 MoE：参数很多，但每次只激活一部分

**MoE（Mixture of Experts，混合专家）** 会把部分网络拆成多个 **Expert（专家）**。

例如：

```text
                 Router
                   │
          ┌────────┼────────┐
          ↓        ↓        ↓
       Expert 1 Expert 2 ... Expert 8
          │        │
          └────┬───┘
               ↓
         选择少数 Expert
               ↓
             输出
```

一个 MoE 模型可能有：

```text
总参数：200B
每个 Token 实际激活：20B
```

所以需要区分：

- **Total Parameters（总参数量）**：模型一共有多少参数；
- **Active Parameters（激活参数量）**：一次 Token 计算真正参与计算的参数。

### 1.3 Dense vs MoE

| 对比项 | Dense | MoE |
|---|---|---|
| 参数使用 | 大部分参数都参与 | 每次只激活部分 Expert |
| 总参数 | 通常等于主要计算规模 | 可以非常大 |
| 单 Token 计算量 | 与总参数高度相关 | 更接近激活参数量 |
| 模型容量 | 参数规模决定 | 可以用大量 Expert 扩大容量 |
| 核心机制 | 直接计算 | Router 负责 Expert 路由 |
| 工程复杂度 | 相对简单 | 更复杂 |
| 多卡要求 | 较高 | 通常更高 |
| 典型特点 | 稳定、直接 | 参数多但计算可控 |

**最重要的一句话：**

> Dense 是“有多少参数，基本就用多少参数算”；MoE 是“模型参数可以很多，但每次只挑一部分 Expert 来算”。

# 2. INT4 量化是什么？

## 2.1 为什么需要量化？

假设模型参数使用 **FP16**：

```text
1 Parameter = 16 bit = 2 Byte
```

70B 模型：

```text
70B × 2 Byte
≈ 140GB
```

所以一个 70B FP16 模型，仅模型权重就大约需要 140GB，实际运行还需要额外显存。

如果使用 **INT4**：

```text
1 Parameter ≈ 4 bit = 0.5 Byte
```

那么：

```text
70B × 0.5 Byte
≈ 35GB
```

所以可以粗略理解：

```text
70B FP16
≈ 140GB

70B INT8
≈ 70GB

70B INT4
≈ 35GB
```

> 注意：这是理想化的权重大小计算。真实量化模型还会有 **scale、zero point / quantization metadata、对齐、运行时 buffer** 等额外开销，因此实际显存不会刚好等于 35GB。

---

## 2.2 INT4 到底做了什么？

原来的 FP16：

```text
0.137
-0.821
1.294
...
```

每个参数占 16 bit。

量化后，不再直接保存完整的 FP16 数值，而是：

```text
4-bit Integer
+
Scale 等量化信息
```

可以粗略理解为：

```text
原始浮点数
   ↓
找到一组数值范围
   ↓
映射到 0~15
   ↓
保存 4-bit 数值
   ↓
配合 Scale 恢复近似浮点值
```

因此：

> **量化不是简单“删除参数”，而是用更少的 bit 表示原来的数值。**

---

# 3. INT4 是否意味着 40G 显卡能直接跑 70B？

这是前面最容易产生误解的地方。

理论上：

```text
70B × 4bit ≈ 35GB
```

所以：

```text
40GB GPU
```

从“模型权重大小”来看，**可能能够加载 70B INT4**。

但是：

> **模型权重显存 ≠ 实际运行显存。**

实际显存还包括：

```text
模型权重
+
KV Cache
+
Activation
+
CUDA / Framework Runtime
+
Temporary Buffer
+
通信 Buffer
+
其他开销
```

因此：

```text
70B INT4 ≈ 35GB
```

并不代表：

```text
40GB GPU 一定可以稳定运行任何 70B INT4 场景。
```

尤其当：

```text
Context Length ↑
Batch Size ↑
并发 ↑
```

**KV Cache** 会明显增加。

---

# 4. QLoRA 是什么？

**QLoRA（Quantized Low-Rank Adaptation）** 可以简单理解成：

> **“把大模型以低比特量化的方式放着，同时只训练很小的 LoRA Adapter。”**

它不是重新训练整个 70B 模型。

基本思路：

```text
70B Base Model
      │
      ↓
4-bit Quantization
      │
      ↓
冻结 Base Model
      │
      ├──────────────┐
      │              │
      ↓              ↓
  不训练          LoRA Adapter
                     │
                  训练参数
                     │
                     ↓
                 最终适配
```

核心优势：

- Base Model 占用显存显著下降；
- Base Model 参数冻结；
- 只训练 LoRA 参数；
- 可以在有限 GPU 资源上微调较大的模型。

---

# 5. QLoRA 的量化需要开发者自己定义吗？

一般 **不需要自己发明量化算法**。

实际工程中通常直接使用成熟组件，例如：

- **bitsandbytes**
- **Transformers**
- **PEFT**

开发者主要做的是：

1. 指定模型；
2. 指定量化配置；
3. 指定 LoRA 配置；
4. 配置训练参数；
5. 启动训练。

例如常见的 QLoRA 配置思路：

```python
from transformers import BitsAndBytesConfig

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,
)
```

这里几个专业名词需要记住：

| 配置 | 含义 |
|---|---|
| `load_in_4bit` | 以 4-bit 方式加载权重 |
| `NF4` | QLoRA 常用的 4-bit NormalFloat 数据类型 |
| `compute_dtype` | 实际计算时使用的精度，例如 BF16 |
| `double_quant` | 对量化相关的量化信息进一步压缩 |

所以：

> **开发者通常定义“我要使用 NF4 + 4bit + BF16 计算”，而不是自己实现整个量化算法。**

---

# 6. 一个关键认知：4-bit 存储，不代表全程 4-bit 计算

这是理解量化的关键。

很多人会误以为：

```text
INT4 权重
×
INT4 输入
=
INT4 计算
```

实际情况往往不是这么简单。

可以粗略理解成：

```text
磁盘 / 显存
      ↓
4-bit Quantized Weight
      ↓
必要时解量化 / Kernel 内部处理
      ↓
BF16 / FP16 等计算
      ↓
结果
```

所以：

> **量化主要首先解决的是“权重怎么存得更小”，并不等于整个模型运行过程都只有 4-bit。**

具体计算路径取决于模型、量化格式和 GPU Kernel。

# 7. 两张 40G GPU 跑 70B INT4

假设：

```text
GPU 0：40GB
GPU 1：40GB
```

不能简单理解成：

```text
40GB + 40GB = 一块 80GB GPU
```

正确理解是：

```text
GPU 0                    GPU 1
40GB                     40GB
┌──────────────┐         ┌──────────────┐
│ 模型的一部分 │         │ 模型的一部分 │
└──────────────┘         └──────────────┘
        │                       │
        └──── GPU Communication ┘
```

也就是：

> **两张卡各自拥有自己的显存，模型通过并行策略被拆开。**

---

# 8. 多卡最重要的几种并行方式

## 8.1 Model / Layer Parallelism

最容易理解：

```text
GPU 0
Layer 0~39

GPU 1
Layer 40~79
```

数据流：

```text
Input
  ↓
GPU 0
Layer 0~39
  ↓
GPU 间通信
  ↓
GPU 1
Layer 40~79
  ↓
Output
```

特点：

> **按层拆模型。**

优点：

- 简单；
- 主要解决“模型放不下”的问题。

缺点：

- GPU 之间可能存在等待；
- GPU 利用率不一定高；
- 通信和流水问题会影响性能。

---

# 9. Tensor Parallelism（TP）

这是大模型多卡推理非常重要的技术。

它不是：

```text
GPU 0：前半层
GPU 1：后半层
```

而是：

> **同一个 Transformer Layer 内部，就让多张 GPU 一起计算。**

例如一个巨大矩阵：

```text
W
```

拆成：

```text
W = [W0 | W1]
```

然后：

```text
GPU 0 → W0
GPU 1 → W1
```

计算：

```text
Y = XW
```

拆成：

```text
GPU 0：Y0 = XW0

GPU 1：Y1 = XW1
```

然后通过 GPU 间通信组合结果。

---

# 10. TP 为什么比简单按层拆更适合高性能推理？

按层拆：

```text
GPU 0：██████████
GPU 1：          ██████████
```

TP：

```text
GPU 0：████████████████
GPU 1：████████████████
```

所以：

> **TP 的目标不仅是“把模型塞进多张 GPU”，还要让多张 GPU 同时参与同一个 Layer 的计算。**

但是代价是：

> **GPU 间通信更多。**

因此存在：

```text
计算收益
   VS
通信成本
```

的权衡。

---

# 11. Attention 如何做 TP？

假设一个模型有：

```text
32 Attention Heads
```

两张 GPU 可以粗略理解为：

```text
GPU 0：
Head 0~15

GPU 1：
Head 16~31
```

于是：

```text
               Hidden States
                     │
          ┌──────────┴──────────┐
          ↓                     ↓
       GPU 0                  GPU 1
     Head 0~15              Head 16~31
          │                     │
          ↓                     ↓
      Attention              Attention
          │                     │
          └──────────┬──────────┘
                     ↓
                  合并结果
```

实际框架会根据模型结构和 TP 实现选择具体切分方式，但核心思想就是：

> **把 Attention 的大计算拆给不同 GPU 并行完成。**

---

# 12. MLP / FFN 也可以做 TP

Transformer Layer 中：

```text
Attention
   ↓
MLP / FFN
```

MLP 通常也包含非常大的矩阵，因此可以进行 Tensor Parallel：

```text
                 X
          ┌──────┴──────┐
          ↓             ↓
       GPU 0          GPU 1
       MLP 0           MLP 1
          │             │
          └──────┬──────┘
                 ↓
             通信 / 合并
                 ↓
             Next Layer
```

---

# 13. Pipeline Parallelism（PP）

**Pipeline Parallelism** 可以理解成流水线。

例如：

```text
GPU 0：
Layer 0~19

GPU 1：
Layer 20~39
```

然后把多个 **Micro-batch** 依次送入：

```text
GPU 0
  ↓
GPU 1
```

当 GPU 0 开始处理下一个 Micro-batch 时：

```text
GPU 0：Batch B
GPU 1：Batch A
```

这样可以提高流水线利用率。

简单记：

> **TP：一层拆给多张 GPU。**
>
> **PP：不同层放到不同 GPU，形成流水线。**

---

# 14. Data Parallelism（DP）

Data Parallelism 不主要解决“一个模型放不下”。

它更像：

```text
GPU 0：
完整模型

GPU 1：
完整模型
```

然后：

```text
数据 A → GPU 0
数据 B → GPU 1
```

所以：

> **DP 主要解决吞吐量问题，而 TP / PP / Model Parallel 更适合解决大模型规模问题。**

---

# 15. 多卡通信：PCIe / NVLink / NCCL

多张 GPU 并不是共享一个显存池。

它们需要互相传数据：

```text
GPU 0
  │
  │ GPU Communication
  ↓
GPU 1
```

常见硬件通道：

- **PCIe**
- **NVLink**
- 更复杂服务器中的 **NVSwitch** 等。

而 NVIDIA 软件层的重要组件：

> **NCCL（NVIDIA Collective Communications Library）**

可以理解成：

> **GPU 之间的高速“通信系统”。**

---

# 16. NCCL 主要做什么？

常见 Collective Communication：

- **AllReduce**
- **AllGather**
- **ReduceScatter**
- **Broadcast**

### AllGather

GPU 0：

```text
[A B]
```

GPU 1：

```text
[C D]
```

AllGather 后：

```text
GPU 0 → [A B C D]
GPU 1 → [A B C D]
```

即：

> 大家把各自的数据收集起来，最后每个人都有完整数据。

### AllReduce

GPU 0：

```text
[1,2,3]
```

GPU 1：

```text
[4,5,6]
```

AllReduce Sum：

```text
[5,7,9]
```

最后两张 GPU 都拿到：

```text
[5,7,9]
```

---

# 17. TP 为什么需要 NCCL？

例如：

```text
GPU 0 → 局部计算结果 Y0

GPU 1 → 局部计算结果 Y1
```

接下来需要：

```text
GPU 0 ↔ GPU 1
```

把结果进行：

```text
AllReduce
或
AllGather
```

于是：

```text
GPU 0
  │
  ├── 局部结果
  │
  └────────┐
           │
         NCCL
           │
  ┌────────┘
  │
GPU 1
  │
  └── 局部结果
```

因此：

> **Tensor Parallelism = 计算拆分 + GPU 并行 + 集合通信。**

---

# 18. Rank / World Size

分布式系统中经常看到：

```text
Rank 0
Rank 1
```

两张 GPU 时可以简单理解：

```text
Rank 0 → GPU 0
Rank 1 → GPU 1
```

而：

```text
World Size = 2
```

表示总共有两个参与分布式计算的进程 / Rank。

---

# 19. 为什么两张 GPU 不一定等于两倍速度？

因为存在通信成本。

例如：

```text
计算：10ms
通信：1ms
```

还不错。

但如果：

```text
计算：2ms
通信：5ms
```

那么大量时间都花在：

> **GPU 之间搬数据**

而不是计算模型。

因此：

> **多卡的性能不仅取决于 GPU 性能，也取决于 GPU 间通信带宽和拓扑。**

所以：

```text
2 × 40GB GPU
```

显存容量相同，并不代表：

```text
2 × 40GB GPU A
=
2 × 40GB GPU B
```

实际多卡性能。

# 20. vLLM 中的 TP

如果目标是正式部署 LLM 推理，可以使用 **vLLM**。

典型思路：

```bash
vllm serve your-model \
    --tensor-parallel-size 2
```

其中：

```text
--tensor-parallel-size 2
```

就是：

> 使用 2 张 GPU 做 Tensor Parallel。

可以理解成：

```text
                  vLLM
                    │
             Tensor Parallel
               ┌────┴────┐
               ↓         ↓
             GPU 0     GPU 1
               │         │
               └─ NCCL ──┘
```

开发者一般不需要自己写：

```text
GPU 0 → GPU 1
AllReduce
AllGather
```

这些底层通信通常由：

```text
vLLM
↓
PyTorch / CUDA
↓
NCCL
```

等组件完成。

# 21. Transformers 中的 device_map

如果只是做开发、测试或简单的大模型加载，可以使用：

```python
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    device_map="auto"
)
```

然后：

```python
print(model.hf_device_map)
```

查看模型实际被分配到了哪些 GPU。

它更像：

> **“帮我把模型合理地放进多张 GPU。”**

而 vLLM 的 TP 更偏向：

> **“让多张 GPU 协同完成高性能推理。”**

二者不要混为一谈。

# 22. 70B INT4 + 2×40G 的完整理解

假设：

```text
GPU 0：40GB
GPU 1：40GB

Model：70B
Quantization：INT4
```

粗略：

```text
70B × 4bit
≈ 35GB 权重
```

如果使用 TP=2，可以把权重和计算拆到两张卡。

概念上：

```text
                 70B INT4
                     │
              Tensor Parallel
                     │
           ┌─────────┴─────────┐
           ↓                   ↓
        GPU 0                GPU 1
         40GB                  40GB
           │                   │
           │      NCCL         │
           └─────────↔─────────┘
                     │
                  推理结果
```

注意：

> **不是把 40GB + 40GB 变成一个物理 80GB 显存。**

而是：

> **模型被拆分并分布在两张 GPU 上。**

---

# 23. KV Cache：为什么模型权重不是全部显存？

LLM 推理还需要：

> **KV Cache**

在 Transformer Attention 中，过去 Token 的：

```text
K（Key）
V（Value）
```

可以缓存下来。

这样生成下一个 Token 时，不需要把历史 Token 的相关计算全部重新做一遍。

因此：

```text
显存需求
=
模型权重
+
KV Cache
+
Activation
+
Runtime
+
Temporary Buffer
+
其他开销
```

而 KV Cache 通常会随着：

```text
Context Length ↑
Batch Size ↑
并发请求 ↑
```

而增加。

所以：

```text
70B INT4 ≈ 35GB
```

不能直接推出：

```text
40GB GPU 一定可以无限上下文 + 高并发运行。
```

# 24. 一次 Token 生成时发生了什么？

可以用一个简化流程理解：

```text
用户请求
   ↓
Tokenizer
   ↓
Token IDs
   ↓
Transformer Layer
   │
   ├── GPU 0：部分计算
   │
   ├── GPU 1：部分计算
   │
   └── NCCL：必要时进行 GPU 间通信
   ↓
下一层
   ↓
...
   ↓
LM Head
   ↓
Logits
   ↓
Sampling
   ↓
生成一个 Token
   ↓
KV Cache 更新
   ↓
继续生成下一个 Token
```

所以“输出一句话”其实是：

```text
Token 1
 ↓
Token 2
 ↓
Token 3
 ↓
...
```

不断重复推理过程。

| **NF4** | QLoRA 中常见的 4-bit 数据类型 |
| **QLoRA** | 4-bit 量化基础模型 + LoRA 微调 |
| **LoRA** | 冻结原模型，只训练低秩 Adapter |
| **TP** | 一个 Layer 内部拆给多张 GPU 一起算 |
| **PP** | 不同 Layer 放到不同 GPU，形成流水线 |
| **DP** | 每张 GPU 放模型副本，处理不同数据 |
| **NCCL** | NVIDIA GPU 间集合通信库 |
| **AllReduce** | 多卡合并数据，并让各卡获得结果 |
| **AllGather** | 收集各卡数据，让每卡获得完整数据 |
| **Rank** | 分布式计算中的进程 / GPU 编号 |
| **World Size** | 参与分布式计算的总进程数 |
| **KV Cache** | 缓存历史 Token 的 K/V，避免重复计算 |
| **vLLM** | 面向 LLM 高性能推理的服务框架 |
| **device_map** | 将模型模块分配到不同设备 |
| **Tensor Parallel Size** | TP 使用的 GPU 数量 |

# 28. 对“两张 40G 跑 70B INT4”的最终结论

对于：

```text
2 × 40GB GPU
70B INT4
```

可以这样理解：

```text
                 70B Model
                     │
                 INT4 Quant
                     │
              ≈ 35GB 权重
                     │
                     ↓
              Tensor Parallel
                ┌────┴────┐
                ↓         ↓
             GPU 0      GPU 1
             40GB       40GB
                │         │
                └─ NCCL ──┘
                     │
                Transformer
                     │
                 KV Cache
                     │
                  Output
```

**结论：**

1. **70B INT4 的权重理论大小约 35GB**，所以量化确实可以显著降低显存需求。
2. **两张 40G 不等于一张物理 80G GPU**，而是通过模型并行把工作分布到两张卡。
3. 如果只是想把模型放进去，可以考虑 **`device_map="auto"`**。
4. 如果要做更正规的高性能推理，可以考虑 **vLLM + Tensor Parallel（TP=2）**。
5. **NCCL** 负责底层 GPU 集合通信。
6. 真正部署时不能只计算模型权重，还必须考虑 **KV Cache、Runtime、Activation 和通信开销**。
7. **量化解决“模型太大”的问题，多卡解决“单卡放不下 / 需要并行计算”的问题；二者可以组合使用。**
8. **TP 并不是简单把显存相加，而是把模型计算拆分，并通过 GPU 间通信协同完成。**
