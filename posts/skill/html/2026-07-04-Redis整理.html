Redis

经典三问题

缓存穿透

1、概念：频繁请求数据库不存在的数据导致数据库宕机

2、解决方案：

两个方面

1、缓存空值


2、布隆过滤器（存在缺陷）

缓存击穿

1、概念：热点数据过期，导致大量请求直接访问数据库，造成的数据库宕机

2、解决方案

三个方面：

1、缓存空值


2、布隆过滤器


3、网关限流/业务限流（网关使用Sentinel/业务使用锁）

缓存雪崩

1、概念：大量缓存同时过期或redis服务不可用，导致全部查询数据库，数据库宕机

2、解决方案

三个方面：

1、网关限流/业务限流（网关使用Sentinel/业务使用锁）


2、对key设置随机过期时间，避免大量key在同一时间实效


3、构建集群架构

引申问题

布隆过滤器

设计思想

1、我们真正刚需：百分百准确识别「不存在的数据」，直接拦截，不走 DB；

2、可以接受极小概率误判「不存在的数据误以为存在」，命中后二次查库兜底即可；


3、目标：极致压缩内存，牺牲 100% 精准存在判断，换取极低内存开销；


4、实现手段：不存原始数据，只用二进制 bit 标记，多个元素共用 bit 位节约空间。



结果：


商品A哈希后位置1，2，3。商品B哈希后位置也是1，2，3。如果商品A售完要删除，此时会导致商品B也会受影响。


所以不允许删除

优点

  • 内存占用低
  • 插入、查询速度快，性能稳定
  • 无法反向解析原始数据，有隐私性
  • 没有哈希冲突的性能退化问题

缺点

  • 存在误判，判定“存在”后，必须二次查库校验
  • 不能删除数据，只能新增
  • 容量需要提前预估，数据超量误判暴增
  • 无法精确统计元素总数

适用场景

  • 秒杀场景，存储热点商品id
  • 爬虫URL去重
  • 黑名单拦截

解决方案

布隆过滤器存储全部有效商品，做第一层拦截；

单独用 Redis Set 存储已下架商品 ID；

查询逻辑：

① 布隆判断不存在 → 直接返回空；

② 布隆判断存在 → 再判断是否在「下架黑名单 Set」；

③ 在黑名单 → 返回空；不在 → 查询 Redis/DB。

// 注入布隆过滤器、redis黑名单set

RBloomFilter<Long> bloomFilter = redissonClient.getBloomFilter("goods_bloom");


RSet<Long> offShelfSet = redissonClient.getSet("goods_off_shelf_set");



// 查询商品


public GoodsDTO getGoods(Long goodsId) {


    // 第一层：布隆过滤，百分百不存在直接拦截


    if (!bloomFilter.contains(goodsId)) {


        return null;


    }


    // 第二层：过滤已下架商品


    if (offShelfSet.contains(goodsId)) {


        return null;


    }


    // 正常查询缓存、数据库


    String cacheKey = "goods:" + goodsId;


    GoodsDTO cache = stringRedisTemplate.opsForValue().get(cacheKey, GoodsDTO.class);


    if (cache != null) return cache;


    GoodsDTO db = goodsMapper.selectById(goodsId);


    if (db != null) {


        stringRedisTemplate.opsForValue().set(cacheKey, db, 1, TimeUnit.HOURS);


    }


    return db;


}



// 商品下架接口


public void offShelf(Long goodsId) {


    // 仅加入黑名单，不修改布隆过滤器


    offShelfSet.add(goodsId);


    // 删除商品缓存


    stringRedisTemplate.delete("goods:" + goodsId);


}



// 凌晨定时任务：重建布隆过滤器，同步最新上架商品


@Scheduled(cron = "0 0 3   ?")


public void rebuildBloomFilter() {


    // 1. 查询数据库所有上架商品


    List<Long> allOnShelfIds = goodsMapper.selectAllOnShelfId();


    // 2. 删除旧布隆，新建


    bloomFilter.delete();


    bloomFilter.tryInit(allOnShelfIds.size(), 0.001); // 预估数量，误判率0.1%


    // 3. 批量写入


    allOnShelfIds.forEach(bloomFilter::add);


    // 4. 清空黑名单（数据已同步到布隆，黑名单失效）


    offShelfSet.clear();


}

优点：实现简单、性能高、无内存翻倍；

缺点：下架商品会一直在布隆中，靠黑名单兜底，依赖定时任务定期清理。

分布式锁

看门狗机制

背景：为了解决锁过期时间设置太长或太短的问题。 目标：只要客户端持有锁且正常运行，就自动给锁续期，保证锁不会提前过期；客户端宕机后，锁会自动到期释放。 核心运行逻辑 
1、触发条件：加锁时没有显式指定锁的过期时间（leaseTime），自动开启看门狗；如果手动指定了 leaseTime，看门狗不会生效

2、默认过期时长：看门狗模式下，锁的初始过期时间为 30 秒，可通过配置项 lockWatchdogTimeout 自定义


3、续期周期：每隔「锁过期时间的 1/3」执行一次续期。默认 30 秒 TTL 的场景下，每 10 秒续期一次，每次续期都将锁的过期时间重置为 30 秒


4、续期校验：只有当前客户端仍然持有锁（锁的唯一标识匹配），才会执行续期操作


5、停止条件：


客户端主动调用 unlock 释放锁，立即取消看门狗定时任务


客户端宕机 / 与 Redis 断开连接，定时任务无法执行，锁到期后自动释放
原理：redis会新开一个线程来轮询检查业务是否还在进行中，如果在进行中则对锁时间进行增加。 底层实现细节 
1、调度实现：Netty轮询

看门狗的定时续期任务，底层基于 Netty HashedWheelTimer（时间轮） 实现，而非 JDK 原生定时器，优势是：


高性能、低资源开销，适合大量分布式锁的定时调度场景


精度满足秒级续期需求，并发场景下表现远优于线程池调度


2、原子性续期：Lua脚本


续期操作通过 Lua 脚本保证原子性，核心逻辑是：先判断锁是否属于当前客户端 + 线程，匹配则重置过期时间，否则不处理

主从切换锁数据丢失

原因：主节点锁数据未同步到从节点，主节点挂机，从节点没有锁信息，导致锁实效。出现的原因，主从切换，数据丢失

红锁

原理：由于问题是在主从切换时导致的不一致，所以红锁直接去掉这种架构，采用多主节点的单机架构模式，去中心化。同时摈弃集群以及主从架构。直接使用多主投票来设置锁。 注意点：

1、redlock解决的问题是，在主从切换，或者集群切换时导致的锁丢失的问题。所以必须要求使用多节点无状态架构，不能存在主从，集群，哨兵模式

2、依赖本地时钟，当时钟出现异常提前跳跃时，会导致锁提前失效。

3、原生的红锁没有实现自动续期的功能，redisson框架封装并完善了红锁，内置了看门狗机制。

适用场景

1、对性能要求高、能容忍极低概率锁失效的非核心业务，如分布式任务防重、库存扣减兜底、接口幂等校验

2、已有成熟 Redis 运维体系，不想额外引入 ZooKeeper、etcd 等组件的场景

3、业务执行时间短，锁 失效时间(TTL) 可以设置得远大于业务耗时的场景

4、对锁可用性要求极高、不能接受单点故障的场景再考虑 Redlock

不适用场景

1、对锁的安全性有绝对要求，不能接受任何并发冲突的场景

2、对业务时间不可控，容易出现长时间阻塞的情况

3、金融交易、资金结算、核心订单状态变更等强一致要求的核心业务，此类场景应优先选择基于 Raft 协议的 etcd 锁、ZooKeeper 分布式锁

改造方案（在不变更集群架构的情况下）

现有架构：三主三从集群 实现方案

1、主从切换丢锁本身是小概率事件，通过基础优化可将概率降到极低，覆盖 90% 以上的业务场景

1、同步等待优化：开启Redisson的waitForSync配置，加锁成功后通过Redis的WAIT命令，强制等待锁数据同步到至少一个从节点再向客户端返回成功。牺牲1ms左右的延迟，大幅降低主从切换丢锁的概率

2、主从同步优化：保证主从节点同机房部署、关闭RDB/AOF重写期间的同步延迟，设置合理的主从断连重试阈值。


3、业务兜底：核心操作增加幂等校验，比如使用数据库乐观锁（版本号机制），即使极端情况锁丢失，也不会出现脏数据，这是核心业务的必备防护

2、复用现有的集群架构直接使用红锁（主从切换期间依然存在锁丢失的风险，但三个节点同时发生的概率极低）

实现方式：通过哈希标签{}控制三个锁key分别落在三个不同的master分片上，使用Redisson封装的RedissonRedLock工具，只要>=2两个分片加锁成功，就算获取锁成功。

优势：完全复用现有架构，仅改动涉及锁的初始化代码；3个分片同时发生主从切换丢锁的概率极低，基本可以满足大多数的业务需求。

代码实现：

1、预设三个固定标签例如{lock_shard_1}…

2、上线前使用CLUSTER KEYSLOT指令进行验证，确保三个标签分别落在三个分片上。


3、后续代码标签使用确定的三个标签即可，后面跟具体的业务锁key



{lock_shard_1}:order_pay_lock


{lock_shard_2}:order_pay_lock


{lock_shard_3}:order_pay_lock


import org.redisson.Redisson;

import org.redisson.RedissonRedLock;


import org.redisson.api.RLock;


import org.redisson.api.RedissonClient;


import org.redisson.config.Config;



import java.util.concurrent.TimeUnit;



public class ClusterRedLockDemo {



    public static void main(String[] args) {


        // 1. 初始化Redis集群客户端（复用现有3主3从集群）


        Config config = new Config();


        config.useClusterServers()


                .addNodeAddress("redis://127.0.0.1:7001", "redis://127.0.0.1:7002", "redis://127.0.0.1:7003")


                .addNodeAddress("redis://127.0.0.1:7004", "redis://127.0.0.1:7005", "redis://127.0.0.1:7006")


                .setConnectTimeout(50);


        RedissonClient redissonClient = Redisson.create(config);



        // 2. 创建3个独立锁，通过不同哈希标签强制分散到3个不同的Master分片


        // 哈希标签规则：{}内的内容决定key所属的哈希槽，不同标签对应不同分片


        RLock lock1 = redissonClient.getLock("{redlock_1}:order_resource_lock");


        RLock lock2 = redissonClient.getLock("{redlock_2}:order_resource_lock");


        RLock lock3 = redissonClient.getLock("{redlock_3}:order_resource_lock");



        // 3. 组装Redlock实例，3节点的多数派阈值为2


        RedissonRedLock clusterRedLock = new RedissonRedLock(lock1, lock2, lock3);



        try {


            // 4. 加锁：等待时间3s，不指定leaseTime自动开启看门狗续期


            boolean lockSuccess = clusterRedLock.tryLock(3, TimeUnit.SECONDS);


            if (lockSuccess) {


                System.out.println("集群版Redlock加锁成功，执行业务逻辑");


                Thread.sleep(5000);


            } else {


                System.out.println("加锁失败，未达到多数派分片要求");


            }


        } catch (InterruptedException e) {


            Thread.currentThread().interrupt();


        } finally {


            // 5. 全分片解锁，清理残留锁


            clusterRedLock.unlock();


            redissonClient.shutdown();


        }


    }


}

脑裂

可能产生的情况(5种) 
a.网络波动（网络问题）

b.主节点长时间阻塞，导致无法响应心跳（业务服务/服务器问题/网络问题）


c.服务器半死机状态，服务器冻结一些线程，导致无法响应心跳（服务器问题）


d.机房隔离故障（其实还是网络问题）


e.网络配置变更，导致的网络失联（网络问题）
原因：主节点受网络波动影响导致与所有从节点失去连接，从节点重新选举主节点，完成后，网络恢复正常，此时两个主节点，旧的主节点此时会降级为从节点，开始同步新主节点的数据，导致旧主节点的数据丢失。 如何避免

1、核心配置，Redis主节点写配置

# 主节点必须至少连接1个从节点，否则拒绝所有写请求

min-replicas-to-write 1


从节点与主节点的最大复制延迟，超过则视为断开连接，单位秒


min-replicas-max-lag 10



原理：当主节点与所有的从节点全部断开连接，但自己仍能正常提供服务时，拒绝所有的写操作（包括SET加锁等操作），这样不会导致出现双锁的问题。


缺点：牺牲了部分可用性

2、哨兵架构或集群架构

1、哨兵架构为奇数点，必须多数派同意才能进行切换

2、集群架构下，主节点必须与集群多数派主节点保持连通才能接受写请求，少数分区的主节点会自动拒绝写，天然降低脑裂风险

3、业务兜底

核心业务增加幂等操作

Redis架构问题

集群架构与哨兵模式的区别

对比维度哨兵模式（Sentinel）Redis Cluster 集群
核心目标主从架构高可用，仅解决故障转移数据分片扩容 + 内置高可用，解决存储 / 写入瓶颈
数据分布所有节点保存完整全量数据，无分片数据按哈希槽拆分，每个主节点只存部分数据
写入能力单主写，写性能上限为单节点性能，无法横向扩展写多主并行写入，写能力随主节点数量线性扩容
存储上限受单节点内存限制，数据量大时内存溢出多节点分摊数据，支持 TB 级海量数据存储
故障转移组件独立哨兵进程集群，和数据节点分离部署集群内置故障检测、投票机制，无需额外哨兵
最小部署规模1 主 1 从 + 3 哨兵（生产规范）最少 3 主 3 从（3 个主节点才能完成投票选主）
Key 跨节点操作无限制，所有 key 都在同一主，mget / 事务无限制不支持跨槽事务、不支持无 hash tag 的跨槽 mget、lua 多 key 限制
扩容方式只能新增从节点分担读；无法扩容写 / 存储新增主节点，迁移哈希槽，同时扩容读写、存储
客户端访问客户端连接哨兵，哨兵返回当前主节点地址客户端需实现集群路由，自动计算槽位、重定向 MOVED/ASK
数据迁移无在线分片迁移，只能全量备份重建支持在线槽迁移，扩容缩容不中断业务
资源开销从节点全量复制，数据越大，复制带宽 / 内存消耗越高分片存储，单节点数据量小，复制压力更低
运维复杂度简单，适合中小数据量、读多写少业务复杂，槽迁移、集群重平衡、跨 key 限制、分片运维成本更高
总结： 哨兵 Sentinel：单机全量数据 + 自动容灾，解决宕机问题，不解决容量和写并发； Redis Cluster：分布式分片存储 + 自带容灾，同时解决宕机、超大存储、高并发写入三大问题，但存在跨 key 命令限制，运维和开发成本更高。

集群如何构建

最低要求三主三从

原因：


如果是三个主节点构建集群，那么当其中一个主节点挂机时，整个服务将直接进入不可用的状态。其他节点不会也不能直接接管挂机节点的哈希曹的内容


1、底层规则


Redis Cluster 正常服务的前提是：16384 个哈希槽全部处于已分配、且对应节点在线的状态。只要有任意一个哈希槽对应的主节点宕机，且没有从节点可以晋升接管，整个集群默认会进入CLUSTERDOWN状态，所有读写请求都会直接报错。



三主三从架构后，如果有一个主节点挂机，那么对应主节点的从节点会升为主节点，接管挂机节点的哈希曹。不影响业务正常使用。

选举流程

1、主观下线

2、客观下线


3、从节点发起选举


4、多数派投票


5、槽位接管与集群广播


6、旧主节点恢复

持久化机制

RDB（快照）

核心原理
全量二进制快照：在某个时间点，把 Redis 当前内存中所有键值对数据一次性写入磁盘二进制文件（.rdb）。 本质：内存镜像，压缩二进制存储，恢复速度极快。 触发分两种：自动定时触发、手动命令触发。
执行流程
  1. 手动触发
  • 同步阻塞（生产环境不推荐）：主线程直接阻塞式遍历所有数据，创建RDB文件
  • 后台异步（主流方式）
  •      1. Redis主线程调用fork()创建子进程；

      

    1. fork阶段仅复制页表，内存采用Copy-On-Write（COW写时复制），不复制完整内存，速度快；
      2. 

    2. 子进程独占内存快照，循环遍历所有KV，写入临时.rdb文件；
      3. 

    3. 主线程继续正常处理客户端读写；若主线程修改数据，会复制一份旧数据给子进程保留快照；
      4. 

    4. 子进程写完临时文件后，原子替换旧的rdb文件；
      5. 

    5. 子进程退出，通知主线程快照完成。
      6.

  2.    # save 秒数 修改次数

    save 900 1    # 900秒内至少1个key修改，自动执行BGSAVE

  3. 额外自动触发场景
  • 执行FlushDB/FlushAll清库前（未关闭RDB时）生成快照
  • Redis正常shutdown关机时，自动执行save持久化
文件恢复流程
  1. Redis 启动时，检测目录下是否存在 .rdb 文件
  2. 主线程直接加载二进制文件，一次性把全部数据载入内存
  3. 加载完成后接收客户端连接，提供服务
优缺点
  • 优点
    1. 二进制压缩文件，体积小，适合冷备份、异地迁移
    2. 恢复速度远快于AOF，大数据场景重启恢复效率高
    3. 子进程后台持久化，主线程几乎无阻塞
  • 缺点
    1. 存在数据丢失风险：两次快照之间新增的数据完全丢失。例：10分钟快照一次，宕机最多丢10分钟数据
    2. fork子进程时，若内存超大（几十G数据），fork会短暂阻塞主线程
    3. 二进制格式兼容性差：高版本RDB文件，低版本Redis无法读取

AOF（日志）

核心原理
增量操作日志：不存数据结果，只记录所有修改数据的命令（set/hset/del 等读命令不记录），以文本追加方式写入 .aof 文件。

恢复时：重新从头到尾执行 AOF 里全部命令，还原内存数据。

执行流程
阶段 1：命令追加写入
  1. 客户端发送写命令，Redis 执行完内存修改
  2. 将这条命令按 Redis 协议格式，追加到内存 AOF 缓冲区
  3. 根据 appendfsync 策略，决定何时刷盘（3 种刷盘策略）
  • appendfsync always：每条命令执行完立刻刷盘，零丢失，性能极差
  • appendfsync everysec（默认）：每秒一次批量刷盘，最多丢失 1 秒数据，性能均衡
  • appendfsync no：交给操作系统内核自动刷盘，丢失数据不可控
阶段 2：AOF 重写（AOF Rewrite，解决文件膨胀） 解决问题：同 key 反复修改会产生大量冗余命令（set k1 1 → set k1 2 → set k1 3，三条日志冗余），AOF 文件无限变大。

重写原理：不读取旧 AOF，直接读取当前内存数据，生成最小化日志。

重写流程（BGREWRITEAOF 后台执行）：

1. 主线程fork子进程；

    

  1. 子进程遍历当前内存所有KV，生成最简写命令，写入临时aof重写文件；
    2. 

  2. 主线程继续处理请求，新写命令同时写入「原有AOF缓冲区 + AOF重写缓冲区」；
    3. 

  3. 子进程完成重写后，主线程把重写缓冲区积压的增量命令追加到新临时文件；
    4. 

  4. 原子替换旧AOF文件，删除临时文件，重写完成。
    5.
文件恢复流程
  1. Redis 启动读取.aof 文件
  2. 逐条解析、执行文件内所有写命令，还原内存完整数据
  3. 若 AOF 文件损坏，支持 redis-check-aof 工具修复截断损坏日志
优缺点
  • 优点
    1. 数据丢失极少：默认每秒刷盘，最多丢 1 秒数据；always 策略零丢失
    2. 文本日志，可读可编辑，误删数据可手动修改文件恢复
    3. 日志追加模式，写入时极少磁盘寻址，写入性能稳定
  • 缺点
    1. AOF 文件体积远大于 RDB
    2. 数据恢复速度慢，海量命令逐条回放耗时久
    3. 持续 IO 写入，性能略低于 RDB
    4. 极端场景重写 fork 会短暂阻塞主线程

RDB/AOF 核心区别

  1. 存储内容与形式
维度RDBAOF
存储内容某一刻完整内存数据快照所有修改操作的命令日志
文件格式压缩二进制文件，体积小文本协议日志，体积大
数据模型全量静态镜像增量动态操作流水
  1. 数据丢失风险
  • RDB：两次快照间所有数据丢失，丢失窗口大（分钟级）
  • AOF：everysec 最多丢 1 秒，always 完全不丢，丢失窗口极小
  1. 写入与阻塞机制
  • RDB：BGSAVE 靠 fork 子进程，仅 fork 瞬间短暂阻塞；写入一次性批量 IO
  • AOF：持续增量刷盘，每秒一次批量写入；BGREWRITEAOF 同样 fork 阻塞，日常写入无阻塞
  1. 恢复性能
  • RDB：直接加载二进制镜像，速度极快
  • AOF：逐条回放所有命令，海量数据恢复很慢
  1. 运维与兼容性
  • RDB：二进制不可读，高低版本不兼容，适合备份迁移
  • AOF：文本可读，可手动修改修复，版本兼容性好
  1. 故障恢复能力
  • RDB：文件损坏直接丢失全部快照数据，无修复工具
  • AOF：提供官方工具修复损坏日志，截断损坏部分仍能恢复大部分数据
  1. 性能损耗
  • RDB：低频磁盘 IO，日常几乎无性能消耗
  • AOF：持续高频磁盘写入，CPU、IO 开销更高

生产建议（推荐方案）

方案推荐
  1. 同时开启 RDB + AOF（企业标准方案）
  • AOF 保证数据尽量不丢失
  • RDB 做定时全量快照，用于快速恢复、冷备份
  • Redis 重启时优先加载 AOF（数据更完整）
  1. 仅 RDB：适合缓存场景，允许少量数据丢失，追求高性能快速重启
  2. 仅 AOF：对数据一致性要求极高、完全无法容忍大量丢失数据的业务
注意（风险）：若 Redis 内存极大，且 fork 期间大量写操作，会产生大量内存拷贝，内存占用瞬间翻倍，可能触发 OOM，这是 RDB 与 AOF 重写共同的潜在风险。
风险解决方案

###### 概述

全套解决方案（分为：系统内核优化、Redis 参数优化、业务架构优化、运维兜底四层）

###### 系统内核优化（服务器优化）

  1. Linux服务器默认会开启小页合并（但Redis不适用，所以关闭即可）
  2. 调整服务器内核参数（内核内存回收、脏页、swap、内存分配策略），从底层进行优化

###### Redis参数优化

  1. 将RDB的快照时间延长，避免频繁fork
  2. 将AOF重写最小文件参数调大，大流量业务调整到 128M/256M，降低AOF重写频率
  3. 错开RDB快照和AOF重写的时间
  • 不要让RDB与AOF同时执行，在AOF重写时短暂暂停RDB的fork，在AOF重写完成后再进行RDB的fork
  • 可以定时任务在凌晨手动执行RDB，白天业务依赖AOF。（服务器层面的定时任务）
  1. 限制Redis的最大内存，为fork提前预留。例：服务器32G内存，Redis限制最大16G，预留8G给fork子进程

###### 业务流量优化

  1. 定时持久化操作（手动 bgsave、定时重写）全部放在凌晨业务低峰，业务代码层面的定时任务
  2. 大促、流量峰值时段关闭自动 RDB 快照，仅保留 AOF 持久化，峰值结束再恢复自动快照

###### 业务架构优化

  1. Redis集群分片：将海量数据拆分多个小分片，单个实例 fork 内存翻倍也不会耗尽机器内存。
  2. 主从分离，从节点执行 RDB 备份
  • 主节点只开启 AOF，关闭自动 RDB save 规则，主库完全不 fork
  • 从节点定时执行BGSAVE生成 rdb 用于备份、恢复
  • 优势：主库无 fork 阻塞、无内存翻倍风险，业务写入完全不受持久化备份影响
  1. 替代方案：使用云服务将运维风险转移给三方厂商

###### 监控告警（运维优化）

  1. 监控指标
  • Redis used_memory_rss：实际物理内存占用，fork 后翻倍立即告警
  • 机器内存使用率、swap 使用量
  1. 告警阈值
  • 机器内存使用率超过 70% 触发预警，超过 85% 紧急告警
  • 持久化磁盘剩余 20% 触发告警，防止磁盘打满持久化崩溃

###### 补充应急方案：已经出现 OOM 临时缓解

  1. 重启服务
  2. 临时注释 redis.conf 中 save 规则，关闭自动 RDB，仅保留 AOF
  3. 调高auto-aof-rewrite-min-size参数，暂停 AOF 自动重写
  4. 扩容机器物理内存，或拆分实例
  5. 业务限流
