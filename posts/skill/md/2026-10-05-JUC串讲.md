# JUC串讲

> 从 `synchronized`、`volatile`、CAS，一路串到 AQS、`ReentrantLock`、`ReentrantReadWriteLock`、`StampedLock`，建立完整的 Java 并发知识体系。

---

## 1. 为什么要学习这条线

Java 并发并不是一堆相互独立的 API。

从底层思想到上层工具，它们实际上一直在解决三个核心问题：

1. **可见性**：一个线程修改的数据，其他线程能不能及时看到？
2. **原子性**：多个线程同时修改数据，会不会产生错误？
3. **互斥与同步**：多个线程同时执行共享代码时，应该怎么协调？

围绕这些问题，可以形成一条非常重要的学习主线：

```text
synchronized
   ↓
volatile
   ↓
CAS
   ↓
AQS
   ↓
ReentrantLock
   ↓
ReentrantReadWriteLock
   ↓
StampedLock
```

需要注意：

> 这不是严格意义上的“前一个技术实现后一个技术”，而是一条非常适合学习的“并发问题逐步深入”路线。

其中：

```text
volatile / synchronized
        ↓
   Java 内存模型

CAS
        ↓
   原子更新思想

AQS
        ↓
   同步器基础框架

ReentrantLock
        ↓
   AQS 独占模式

ReentrantReadWriteLock
        ↓
   AQS 共享 + 独占模式

StampedLock
        ↓
   乐观读思想
```

而且还有一个必须注意的点：

> `ReentrantLock` 和 `ReentrantReadWriteLock` 都基于 AQS，而 `StampedLock` 并不是基于 AQS 实现的。

---

# 2. 多线程到底为什么会出问题

先看最简单的代码：

```java
int count = 0;
```

多个线程同时执行：

```java
count++;
```

很多人第一反应是：

```text
count = count + 1
```

但从并发角度看，它至少包含：

```text
读取 count
    ↓
执行 +1
    ↓
写回 count
```

例如：

```text
初始 count = 0

线程 A：读取 0
线程 B：读取 0

线程 A：0 + 1 = 1
线程 B：0 + 1 = 1

线程 A：写入 1
线程 B：写入 1
```

最终：

```text
count = 1
```

但我们期望：

```text
count = 2
```

于是产生了三个非常核心的并发问题：

```text
可见性
原子性
有序性
```

---

# 3. 第一层：synchronized

## 3.1 synchronized 是什么

`synchronized` 是 Java 最基础的同步机制之一。

它最核心的思想：

> **同一时刻，只允许一个线程进入被保护的临界区。**

例如：

```java
public synchronized void increment() {
    count++;
}
```

或者：

```java
synchronized (lock) {
    count++;
}
```

多个线程执行时：

```text
线程 A
  ↓
获取锁
  ↓
进入临界区
  ↓
修改数据
  ↓
释放锁

线程 B
  ↓
等待
  ↓
获取锁
  ↓
进入临界区
```

因此可以保证：

```text
同一时刻只有一个线程修改共享数据
```

---

## 3.2 synchronized 解决了什么

可以先记住两个核心能力：

```text
互斥 + 可见性
```

### 互斥

进入临界区的线程是互斥的：

```text
线程 A：执行
线程 B：等待
线程 C：等待
```

这样可以防止多个线程同时修改共享数据。

### 可见性

`synchronized` 与 Java 内存模型中的 `happens-before` 规则有关。

简单理解：

> 一个线程释放某个锁，另一个线程随后成功获取同一个锁，那么前一个线程在释放锁之前对共享变量的修改，对后一个线程是可见的。

因此，`synchronized` 不只是“让线程排队”，它同时提供了内存可见性保障。

---

## 3.3 synchronized 的局限

假设有一个缓存：

```java
Map<String, Object> cache;
```

有 100 个线程都只是读取：

```java
cache.get("name");
```

如果把读取方法也全部放进 `synchronized`：

```text
线程 A：读取
线程 B：等待
线程 C：等待
线程 D：等待
```

即使多个线程只是读取，也必须串行。

于是出现了一个问题：

> **读操作之间其实不一定需要互斥，能不能让多个线程同时读？**

这为后面的读写锁埋下了伏笔。

---

# 4. 第二层：volatile

## 4.1 volatile 是什么

如果我们的核心需求只是：

> 一个线程修改变量以后，其他线程能够及时看到。

这时候可以考虑：

```java
volatile
```

例如：

```java
private volatile boolean running = true;
```

线程 A：

```java
running = false;
```

线程 B：

```java
while (running) {
    // ...
}
```

`volatile` 可以保证线程 B 能看到线程 A 对 `running` 的修改。

---

## 4.2 volatile 主要解决什么

可以先记成：

```text
volatile
   ↓
可见性 + 一定程度上的有序性约束
```

但是有一个非常重要的结论：

> **volatile 不保证复合操作的原子性。**

---

## 4.3 为什么 volatile 不能保证 count++

例如：

```java
volatile int count;
```

下面的操作依然不安全：

```java
count++;
```

因为：

```text
count++
```

本质上还是：

```text
读
+
计算
+
写
```

两个线程仍然可能：

```text
线程 A：读取 0
线程 B：读取 0

线程 A：计算 1
线程 B：计算 1

线程 A：写入 1
线程 B：写入 1
```

所以：

```text
volatile ≠ 原子操作
```

这时问题进一步变成：

> 有没有办法在不依赖完整互斥锁的情况下，让某些更新操作原子完成？

于是进入 CAS。

---

# 5. 第三层：CAS

## 5.1 CAS 是什么

CAS：简单来说就是比较并交换，是一种乐观锁的思想

```text
Compare And Set
Compare And Swap
```

核心思想：

> **我认为当前值还是 X，如果它确实还是 X，就把它修改成 Y；否则修改失败。**

可以抽象成：

```text
if (current == expected) {
    current = newValue;
    success;
} else {
    fail;
}
```

关键在于：

```text
比较 + 修改
```

这一过程具有原子性。

---

## 5.2 CAS 如何保证 count 的更新

假设：

```text
count = 0
```

线程 A：

```text
读取 count = 0

CAS(
    expected = 0,
    newValue = 1
)
```

成功以后：

```text
count = 1
```

如果线程 B 之前也读取到了：

```text
count = 0
```

然后 B 执行：

```text
CAS(
    expected = 0,
    newValue = 1
)
```

由于此时：

```text
count = 1
```

因此 B 的 CAS 失败。

B 可以重新读取：

```text
读取 1
    ↓
计算 2
    ↓
CAS(1, 2)
    ↓
成功
```

最终得到：

```text
count = 2
```

---

## 5.3 CAS 为什么重要

Java 中很多原子类都大量使用 CAS 思想：

```java
AtomicInteger
AtomicLong
AtomicReference
```

例如：

```java
AtomicInteger count = new AtomicInteger();

count.incrementAndGet();
```

其核心思想可以理解为：

```text
读取旧值
    ↓
计算新值
    ↓
CAS
    ↓
失败？
    ↓
重新尝试
```

这种“失败后继续尝试”的过程通常称为：

> **自旋**

---

## 5.4 CAS 与 synchronized 的区别

### synchronized

```text
获取锁
   ↓
抢不到
   ↓
阻塞等待
```

可以理解成：

> “拿不到，就等。”

### CAS

```text
尝试修改
   ↓
失败
   ↓
再试
   ↓
失败
   ↓
继续试
```

可以理解成：

> “拿不到，就再试。”

所以 CAS 非常适合一些更新逻辑简单、竞争程度不高的场景。

---

## 5.5 CAS 的局限

CAS 并不是万能的。

高竞争场景下：

```text
100 个线程
同时更新一个变量
```

可能出现：

```text
线程 1：成功
线程 2：失败
线程 3：失败
线程 4：失败
...
线程 100：失败
```

大量失败线程不断重试：

```java
while (...) {
    compareAndSet(...);
}
```

会造成：

> **CPU 自旋消耗。**

于是又产生了一个新的问题：

> CAS 抢不到时，能不能让线程排队等待，而不是一直消耗 CPU？

这就进入 AQS。

---

# 6. 第四层：AQS

## 6.1 AQS 是什么

AQS：

```text
AbstractQueuedSynchronizer
```

可以把它理解成：

> **一个用于构建锁和其他同步器的基础框架。**

AQS 本身通常不是直接使用的业务锁，而是提供一套通用能力：

```text
state
+
CAS
+
等待队列
+
阻塞
+
唤醒
+
独占模式
+
共享模式
```

---

# 7. AQS 的核心：state

AQS 中最重要的成员之一：

```java
int state;
```

先把 `state` 理解成：

> **同步状态。**

但是：

> `state` 具体表示什么，由具体的同步器定义。

例如：

### ReentrantLock

```text
state = 锁的重入次数
```

### Semaphore

```text
state = 当前剩余许可
```

### CountDownLatch

```text
state = 剩余计数
```

### ReentrantReadWriteLock

```text
state = 读锁 + 写锁相关状态
```

因此 AQS 的设计非常抽象：

> **AQS 不关心你实现的是锁、信号量还是倒计时器，它只负责提供统一的状态管理、排队、阻塞和唤醒机制。**

---

# 8. AQS 为什么需要队列

假设 100 个线程竞争一个锁。

如果纯粹使用 CAS：

```text
T1 → CAS
T2 → CAS
T3 → CAS
...
T100 → CAS
```

失败线程可能不断自旋。

AQS 的思路是：

```text
先尝试 CAS 获取
        ↓
成功
        ↓
直接执行

失败
 ↓
进入等待队列
 ↓
阻塞线程
 ↓
等待前驱线程释放
 ↓
被唤醒
 ↓
再次尝试
```

可以把它浓缩成：

```text
抢
 ↓
失败
 ↓
排队
 ↓
阻塞
 ↓
被唤醒
 ↓
再抢
```

这就是 AQS 设计的核心思想之一。

---

# 9. AQS 与 CAS 的关系

这两个知识点一定要联系起来。

可以简单理解成：

```text
CAS
 ↓
负责原子地修改 state

AQS
 ↓
发现 CAS 抢不到
 ↓
让线程进入队列
 ↓
避免线程无限自旋
```

因此：

> **CAS 负责“怎么原子地抢状态”，AQS 负责“抢不到之后怎么办”。**

---

# 10. AQS 的两种模式

AQS 最重要的两个工作模式：

```text
Exclusive
独占模式

Shared
共享模式
```

## 10.1 独占模式

同一时刻只能有一个线程成功。

典型代表：

```text
ReentrantLock
```

结构：

```text
AQS
 ↓
Exclusive
 ↓
ReentrantLock
```

## 10.2 共享模式

允许多个线程同时获取同步状态。

典型代表：

```text
ReentrantReadWriteLock 的读锁
```

结构：

```text
AQS
 ↓
Shared
 ↓
ReadLock
```

“独占”和“共享”这两个概念，是理解读写锁的关键。

---

# 11. 第五层：ReentrantLock

## 11.1 ReentrantLock 是什么

`ReentrantLock` 可以理解为：

> **基于 AQS 独占模式实现的高级可重入锁。**

对应关系：

```text
AQS
 ↓
Exclusive
 ↓
ReentrantLock
```

---

## 11.2 ReentrantLock 为什么存在

`synchronized` 已经可以加锁，为什么还需要 `ReentrantLock`？

因为 `ReentrantLock` 提供了更丰富的控制能力。

例如：

```java
lock.lock();
```

还可以：

```java
lock.tryLock();
```

以及：

```java
lock.lockInterruptibly();
```

还可以选择公平锁：

```java
new ReentrantLock(true);
```

同时支持：

```java
Condition
```

用于构建更灵活的线程协作机制。

---

# 12. ReentrantLock 的可重入

例如：

```java
lock.lock();

try {
    methodA();
} finally {
    lock.unlock();
}
```

而：

```java
void methodA() {
    lock.lock();

    try {
        // ...
    } finally {
        lock.unlock();
    }
}
```

允许。

可以简单理解成：

```text
线程 A

第一次 lock
   ↓
state = 1

第二次 lock
   ↓
发现持有者还是自己
   ↓
state = 2
```

释放：

```text
unlock
 ↓
state = 1

unlock
 ↓
state = 0
 ↓
真正释放锁
```

所以：

> **可重入锁一定要求“加锁几次，就对应释放几次”。**

---

# 13. ReentrantLock 与 synchronized

| 特性 | synchronized | ReentrantLock |
|---|---|---|
| 互斥 | ✅ | ✅ |
| 可重入 | ✅ | ✅ |
| 可中断获取 | 能力较有限 | ✅ |
| `tryLock()` | ❌ | ✅ |
| 公平锁 | 不能直接配置 | ✅ |
| `Condition` | `wait/notify` | ✅ |
| 编程灵活性 | 较低 | 更高 |

所以：

> `ReentrantLock` 并不是简单地“替代 synchronized”，而是在需要更强控制能力时提供更多选择。

---

# 14. 第六层：ReentrantReadWriteLock

## 14.1 为什么需要读写锁

假设有一个共享缓存：

```text
读取：1000000 次
写入：10 次
```

如果所有操作都用普通互斥锁：

```text
读 → 读 → 读 → 读 → 写
```

全部串行。

但实际上：

```text
读 + 读
```

通常不需要互斥。

于是出现：

```java
ReentrantReadWriteLock
```

它把锁拆成：

```text
ReadLock
WriteLock
```

---

# 15. 读写锁的核心规则

```text
读读：✅
读写：❌
写读：❌
写写：❌
```

也就是：

```text
读锁 → 共享
写锁 → 独占
```

---

## 15.1 多线程可以同时读

例如：

```text
线程 A：读
线程 B：读
线程 C：读
```

可以同时执行。

```text
A ───────
B ───────
C ───────
```

---

## 15.2 写锁必须独占

如果线程 D 想写：

```text
A ───────
B ───────
C ───────

D → 等待
```

直到所有读锁释放。

因此读写锁非常适合**读多写少**的业务！

---

# 16. ReentrantReadWriteLock 与 AQS 的关系

这里是整条知识线中非常关键的连接：

```text
AQS
 │
 ├── Exclusive
 │      ↓
 │  WriteLock
 │
 └── Shared
        ↓
      ReadLock
```

也就是说：

```text
WriteLock
→ 独占模式

ReadLock
→ 共享模式
```

所以读写锁本质上是在 AQS 的能力之上，把**独占 + 共享**组合到同一个同步器中。

---

# 17. 读锁升级和写锁降级

因为存在：

```text
ReadLock
WriteLock
```

自然会出现两个方向：

```text
读 → 写
写 → 读
```

---

## 17.1 读锁升级为写锁

这是非常危险的。

例如：

```text
线程 A：持有读锁
线程 B：持有读锁

A：想升级写锁
B：想升级写锁
```

写锁必须等待所有读锁释放。

于是：

```text
A 等 B
B 等 A
```

可能形成死锁。

所以：

> **不要把“持有读锁”直接升级为“写锁”。**

更加稳妥的方式通常是：

```text
释放读锁
   ↓
获取写锁
   ↓
再次检查条件
   ↓
执行修改
```

这里通常还要注意“重新检查”，因为读锁释放与写锁获取之间可能已经发生了其他线程的修改。

---

## 17.2 写锁降级为读锁

反过来：

```text
写 → 读
```

通常是允许的，这叫：

> **锁降级（Lock Downgrade）**

基本过程：

```text
获取写锁
   ↓
修改数据
   ↓
获取读锁
   ↓
释放写锁
   ↓
继续以读锁方式读取
```

因为开始时线程已经持有独占的写锁，所以这个过程可以安全地完成。

---

# 18. ReentrantReadWriteLock 的 state

这是源码学习中的关键点。

AQS 只有一个：

```java
int state;
```

但是读写锁需要同时保存：

```text
读锁状态 + 写锁状态
```

因此可以把 `state` 理解成拆成两部分：

```text
31             16 15              0
+----------------+----------------+
|   读锁计数      |   写锁计数      |
+----------------+----------------+
       16bit            16bit
```

概念上：

```text
高 16 位：读锁数量
低 16 位：写锁重入次数
```

这样一个 `int` 就可以同时记录：

```text
读锁总数 + 写锁重入次数
```

---

# 19. 为什么读锁还需要线程级别的持有次数

假设：

```text
线程 A：读锁
线程 B：读锁
```

此时：

```text
读锁总数 = 2
```

如果 A 再次获取：

```text
读锁总数 = 3
```

释放时必须知道：

```text
A 释放的是自己的读锁
```

而不能误把其他线程的读锁一起算掉。

因此实现中除了维护全局读锁状态，还会维护线程维度的持有次数。

源码里可以看到类似：

```text
HoldCounter
ThreadLocal
```

这样的设计。

可以简单理解成：

```text
全局：
当前一共有多少个读锁持有者

线程级：
当前线程持有了多少次读锁
```

---

# 20. 读写锁为什么不是任何场景都比普通锁快

一个常见误区：

> “只要读多写少，就一定要使用读写锁。”

并不是。

因为读写锁自身也有额外成本：

```text
读锁状态维护
线程持有状态
同步控制
唤醒与竞争
```

如果：

```text
临界区特别小
线程数量很少
读写比例差不多
```

那么读写锁未必比**ReentrantLock**更快。

因此真正适合读写锁的场景通常是：

```text
读很多 + 写比较少 + 读操作成本不低 + 读操作之间可以安全并发
```

---

# 21. 第七层：StampedLock

## 21.1 为什么还需要 StampedLock

到了读写锁以后，我们继续思考：

> 如果读取特别多，而很多读取只是“快速看一下”，是不是连真正的读锁都不一定需要？

于是出现**StampedLock**，它引入了**写锁 + 读锁 + 乐观读**三种模式。

---

# 22. 什么是乐观读

传统读锁属于：

> **悲观读。**

意思是：

```text
我要读数据
 ↓
先加读锁
 ↓
保证读取期间没人写
```

而 StampedLock 的乐观读思路是：

> **大概率没人修改，我先直接读取，最后再验证读取期间有没有发生写操作。**

基本流程：

```text
开始乐观读
   ↓
读取数据
   ↓
validate
   ↓
是否发生写操作？
 ┌──┴───┐
 否      是
 ↓       ↓
成功使用 重新获取读锁
         ↓
        重新读取
```

---

# 23. StampedLock 示例

例如：

```java
long stamp = lock.tryOptimisticRead();

int x = this.x;
int y = this.y;

if (!lock.validate(stamp)) {
    stamp = lock.readLock();

    try {
        x = this.x;
        y = this.y;
    } finally {
        lock.unlockRead(stamp);
    }
}
```

这段代码的关键点是：

### 第一步

```java
long stamp = lock.tryOptimisticRead();
```

获取一个 stamp。

注意：

> 这并不代表真正获取了读锁。

---

### 第二步

直接读取：

```java
int x = this.x;
int y = this.y;
```

此时写线程理论上仍然可能修改数据。

---

### 第三步

校验：

```java
lock.validate(stamp)
```

如果返回：

```text
true
```

说明这次读取仍然有效。

如果返回：

```text
false
```

说明读取期间发生过相关写操作。

此时刚才的数据不应该继续使用，需要改成真正的读锁并重新读取。

---

# 24. 为什么乐观读可能更快

传统读锁：

```text
获取读锁
 ↓
维护同步状态
 ↓
读取
 ↓
释放读锁
```

乐观读：

```text
获取 stamp
 ↓
直接读取
 ↓
validate
```

如果：

```text
读很多 + 写极少
```

那么大量读取可能直接：

```text
validate = true
```

于是避免了频繁获取真正读锁产生的同步成本。

---

# 25. StampedLock 和 ReentrantReadWriteLock 的区别

虽然两者都能做**读 + 写**，但设计思想已经不完全一样。

## ReentrantReadWriteLock

重点：

```text
可重入 + 读共享 + 写独占 + 公平/非公平
```

## StampedLock

重点：

```text
读锁 + 写锁 + 乐观读 + stamp + validate
```

可以理解为：

> `ReentrantReadWriteLock` 更像“更强的读写锁”，而 `StampedLock` 更像“围绕乐观读重新设计的一套同步机制”。

---

# 26. 一个必须牢记的区别：StampedLock 不可重入

前面两个锁：

```text
ReentrantLock
ReentrantReadWriteLock
```

都是：

```text
✅ 可重入
```

而：

```text
StampedLock
```

是：

```text
❌ 不可重入
```

也就是说，它不能像 `ReentrantLock` 一样，简单地依赖“同一个线程再次加锁就增加持有次数”的机制。

因此在使用 `StampedLock` 时，需要更加严格地管理 stamp 和解锁流程。

# 27. 把整条线串起来

现在重新从最开始看。

## 27.1 第一步：只需要保证可见性

问题：

```text
线程 A 改了变量
线程 B 看不到
```

解决：

```text
volatile
```

核心：

```text
可见性 + 有序性约束
```

---

## 27.2 第二步：需要原子更新

问题：

```text
count++
```

即使使用 volatile 依然不安全。

解决：

```text
CAS
```

核心：

```text
比较 + 原子修改
```

---

## 27.3 第三步：需要临界区互斥

问题：

```text
多个操作必须作为一个整体完成
```

例如：

```java
if (!map.containsKey(key)) {
    map.put(key, value);
}
```

此时单纯一个 CAS 往往不够。

可以使用：

```text
synchronized
```

核心：

```text
互斥 + 可见性
```

---

## 27.4 第四步：CAS 抢不到时怎么办

高竞争情况下，不能无限自旋。

于是：

```text
AQS
```

加入：

```text
state
+
CAS
+
队列
+
阻塞
+
唤醒
```

形成：

```text
先抢
 ↓
失败
 ↓
排队
 ↓
阻塞
 ↓
被唤醒
 ↓
再抢
```

---

## 27.5 第五步：基于 AQS 构造高级独占锁

于是：

```text
AQS
 ↓
Exclusive
 ↓
ReentrantLock
```

获得：

```text
可重入 + tryLock + 可中断 + 公平锁 + Condition
```

等能力。

---

## 27.6 第六步：读和写不应该完全一样

发现：

```text
读 + 读
```

其实可以并发。

所以：

```text
ReentrantReadWriteLock
```

把同步分成：

```text
ReadLock
WriteLock
```

对应：

```text
ReadLock  → Shared
WriteLock → Exclusive
```

于是：

```text
读读：✅
读写：❌
写读：❌
写写：❌
```

实现：

> **多读单写。**

---

## 27.7 第七步：读取非常多，能不能连读锁都少加一些

于是：

```text
StampedLock
```

引入：

```text
Optimistic Read
```

形成：

```text
先读
 ↓
后验证
 ↓
失败再加真正的读锁
```

这就是：

> **乐观并发控制。**

# 29. 从“问题”角度理解这些技术

在真正做项目时，不要先问：

> “这里应该用哪个 API？”

而应该先问：

## 问题一：只是保证一个变量的可见性？

考虑：

```text
volatile
```

---

## 问题二：只是一个简单的原子更新？

考虑：

```text
CAS + Atomic*
```

---

## 问题三：多个操作必须组成一个完整临界区？

考虑：

```text
synchronized
```

或者：

```text
ReentrantLock
```

---

## 问题四：读很多、写很少？

考虑：

```text
ReentrantReadWriteLock
```

---

## 问题五：读特别多，而且读取可以接受“先读后验证”？

考虑：

```text
StampedLock
```

# 30. 横向对比

| 技术 | 核心解决问题 | 是否阻塞 | 是否可重入 | 核心特点 |
|---|---|---:|---:|---|
| `volatile` | 可见性、有序性 | 否 | 不适用 | 不保证复合操作原子性 |
| CAS | 原子更新 | 通常不阻塞 | 不适用 | 比较并更新 |
| `synchronized` | 互斥 + 可见性 | 是 | ✅ | 使用简单 |
| AQS | 构建同步器 | 可阻塞 | 取决于实现 | state + 队列 + CAS |
| `ReentrantLock` | 高级互斥锁 | 是 | ✅ | tryLock、可中断、公平锁、Condition |
| `ReentrantReadWriteLock` | 多读单写 | 是 | ✅ | 读共享、写独占 |
| `StampedLock` | 高并发读场景 | 是 / 乐观读不阻塞 | ❌ | 读、写、乐观读 |

---

# 31. 最终记忆版

快速回忆，可以直接记下面这组关键词：

```text
volatile
    ↓
可见性

CAS
    ↓
原子更新

synchronized
    ↓
互斥

AQS
    ↓
state + CAS + 队列 + 阻塞 + 唤醒

ReentrantLock
    ↓
AQS + 独占 + 可重入

ReentrantReadWriteLock
    ↓
读共享 + 写独占

StampedLock
    ↓
乐观读 + stamp + validate
```

再压缩成一句话：

> **`volatile` 解决“能不能看到”，CAS 解决“能不能原子地改”，`synchronized` 解决“能不能互斥地执行”，AQS 解决“拿不到同步状态以后怎么排队等待”，`ReentrantLock` 是基于 AQS 独占模式实现的高级可重入锁，`ReentrantReadWriteLock` 在此基础上利用共享与独占模式实现多读单写，而 `StampedLock` 又进一步引入乐观读，让读多写少的场景拥有更轻量的读取路径。**

# 33. 一句话总结整个 JUC 串讲

```text
共享变量
   ↓
并发问题
   ↓
可见性 → volatile
   ↓
原子性 → CAS
   ↓
互斥 → synchronized
   ↓
复杂同步 → AQS
   ↓
独占可重入锁 → ReentrantLock
   ↓
多读单写 → ReentrantReadWriteLock
   ↓
乐观读优化 → StampedLock
```

这条线的核心不是记住 7 个类，而是理解：

> **Java 是如何从“一个变量怎么安全修改”，一步一步演进到“多个线程如何高效协作”的。**
