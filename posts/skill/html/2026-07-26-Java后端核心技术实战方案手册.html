Java后端核心技术实战方案手册

一、JVM 线上OOM故障排查与内存调优

1.1 线上OOM标准排查顺序

针对「线上OOM先看日志还是先dump」的问题，按照**「止血保服务 → 定位根因 → 修复验证」**的优先级，标准排查流程如下：

  1. 应急止血（第一优先级）

    • 若服务已完全不可用、持续报错，优先执行切流/重启服务，避免影响线上业务；
    • 重启前务必保留现场：确保JVM配置了-XX:+HeapDumpOnOutOfMemoryError，OOM时会自动生成堆快照文件；同时保留GC日志、应用错误日志。

  2. 初步定位：先看日志与监控

    • 先查看应用错误日志，确认OOM的类型：是堆内存溢出（Java heap space）、永久代/元空间溢出、栈溢出，还是堆外内存溢出；
    • 再查看GC日志与监控指标，观察溢出前的内存趋势：老年代使用率是否持续上涨、Full GC频率是否突增、单次Full GC耗时是否过长，初步判断是「流量突增导致内存不足」还是「内存泄漏」。

  3. 深度分析：堆快照（dump）分析

    • 若服务仍在运行但内存持续上涨，使用jmap -dump:format=b,file=heap.hprof <pid>手动导出堆快照；
    • 使用MAT（Memory Analyzer Tool）、JVisualVM等工具分析dump文件，重点关注：
      • 大对象排行榜：哪些对象占用内存最多；
      • 泄漏嫌疑点：哪些对象被意外持有引用、无法被GC回收；
      • 对象引用链：定位泄漏对象的创建与持有位置。

  4. 根因修复与验证

    • 结合代码定位问题：大对象创建未释放、集合无限扩容、静态变量持有大对象、第三方组件内存泄漏等；
    • 修复后调整JVM参数（堆大小、年轻代比例、GC收集器等），上线后持续监控内存与GC指标。

1.2 老年代占用率飙升核心监控指标

当老年代占用率飙高时，按优先级重点盯以下指标：

  1. Full GC 频率与耗时：最核心指标。正常服务Full GC频率应在数小时一次以上，若几分钟一次、单次耗时超过1秒，说明内存已出现瓶颈；
  2. 老年代使用率增长速率：每次Young GC后，老年代使用率是否持续阶梯式上涨，若是则大概率存在内存泄漏；
  3. 对象晋升速率与年龄：观察Young GC后有多少对象进入老年代，是否存在「对象年龄未达阈值就提前晋升」（比如Survivor区太小）；
  4. 元空间使用率：排除类加载过多导致的非堆内存溢出。

1.3 常用排查命令

# 查看JVM内存概览
jstat -gc <pid> 1000 10  # 每秒打印一次GC统计，共10次
jmap -heap <pid>          # 查看堆内存详细配置与使用情况

# 导出堆快照
jmap -dump:format=b,file=heap_$(date +%Y%m%d%H%M).hprof <pid>

# 查看线程栈，排查是否有线程导致内存问题
jstack <pid> > thread_dump.txt

二、并发编程：线程池核心运行逻辑

2.1 任务提交完整执行链路

针对「核心线程满了放哪？队列满了怎么办？最大线程满了谁干活？」的问题，任务提交后执行流程按顺序如下：

  1. 步骤1：核心线程处理
    提交任务时，若当前运行线程数 < 核心线程数（corePoolSize），直接创建新的核心线程执行任务。

  2. 步骤2：入阻塞队列等待
    若核心线程数已满，将任务加入阻塞队列（workQueue）排队等待，由空闲的核心线程调度执行。

  3. 步骤3：非核心线程扩容
    若阻塞队列也已满，且当前运行线程数 < 最大线程数（maximumPoolSize），创建非核心线程（救急线程）执行任务。

  4. 步骤4：执行拒绝策略
    若当前线程数已达最大线程数，队列也全满，触发拒绝策略（RejectedExecutionHandler），默认抛出异常。

2.2 七大参数对应链路作用

参数 作用 对应链路环节
corePoolSize 核心线程数 长期存活的线程数量 步骤1：任务优先由核心线程处理
maximumPoolSize 最大线程数 线程池允许的最大线程总数 步骤3：队列满后扩容的上限
keepAliveTime 空闲存活时间 非核心线程空闲后的存活时长 步骤3：非核心线程用完后多久回收
unit 时间单位 存活时间的单位 配合keepAliveTime使用
workQueue 阻塞队列 存放等待执行任务的队列 步骤2：核心线程满后任务入队
threadFactory 线程工厂 用于创建线程的工厂 所有线程的创建入口
rejectedExecutionHandler 拒绝策略 线程池满后的处理策略 步骤4：超出承载能力时的兜底

2.3 常见场景调优

  • CPU密集型任务：核心线程数 = CPU核心数，队列不宜过长，避免堆积；
  • IO密集型任务：核心线程数可设为CPU核心数*2，最大线程数可更大，利用IO等待时间；
  • 队列选择：执行短任务用有界队列防OOM，执行长任务可考虑直接扩容（SynchronousQueue）。

三、MySQL慢SQL调优三招实战

3.1 第一招：explain 优先看 type 与 rows

执行explain <SQL语句>后，优先关注两个核心字段，快速判断SQL性能基线：

  1. type列：访问类型
    性能从优到劣排序：system > const > eq_ref > ref > range > index > ALL

    • 合格底线：至少达到range级别（索引范围扫描）；
    • 危险信号：出现ALL（全表扫描），必须优先优化，添加合适索引。

  2. rows列：预计扫描行数
    表示MySQL预估需要扫描多少行才能得到结果，数值越大性能越差。

    • 优化目标：让rows尽量接近实际返回行数，减少无效扫描。

3.2 第二招：Extra 出现 Using filesort 优化方案

Using filesort表示MySQL无法利用索引完成排序，需要在内存/磁盘中进行文件排序，性能损耗大。

优化方法：

  1. 最左前缀匹配：让ORDER BY的字段顺序与联合索引的顺序完全一致，且符合最左前缀原则；
  2. 覆盖索引：查询的字段全部包含在索引中，避免回表，排序直接走索引；
  3. 减少排序数据量：只排序必要字段，避免大字段参与排序；
  4. 特殊场景：若排序数据量极大，可调整sort_buffer_size临时缓解，但本质仍需优化索引。

示例：SQL为select id,name from user where age = 20 order by create_time，建立联合索引idx_age_create_time(age, create_time)，即可消除Using filesort。

3.3 第三招：优化器选错索引的强制修正

当MySQL优化器因统计信息不准、数据分布不均等原因选错索引时，使用强制索引命令手动指定索引。

  1. 强制走指定索引
SELECT * FROM 表名 FORCE INDEX(索引名) WHERE 条件;

强制优化器使用指定索引，忽略其他索引选项。

  1. 建议使用索引
SELECT * FROM 表名 USE INDEX(索引名) WHERE 条件;

给优化器建议，优先级低于FORCE INDEX。

  1. 补充：长效优化
    强制索引是临时方案，长效解决可通过：
    • 执行ANALYZE TABLE 表名更新表统计信息；
    • 调整索引设计，删除冗余、低效索引。

四、Redis 缓存防护与分布式锁方案

4.1 缓存穿透、击穿、雪崩三层防护

按照「事前预防、事中处理、事后兜底」三层架构，三类问题的防护方案如下：

缓存穿透（查询不存在的数据，直接打到数据库）

  • 事前：接口层做参数校验，过滤非法值；引入布隆过滤器，将所有存在的key预先存入，不存在的key直接拦截。
  • 事中：对数据库查不到的数据，在缓存中存入空值（null）并设置短过期时间（如30秒），避免重复打库。
  • 事后：接口增加限流机制，异常IP加入黑名单。

缓存击穿（热点key过期，瞬间流量打穿数据库）

  • 事前：热点数据设置逻辑过期（不设置物理过期时间，后台异步更新），或永不过期；提前预热热点数据。
  • 事中：使用互斥锁（分布式锁），只让一个请求去数据库查数据并更新缓存，其余请求等待重试。
  • 事后：监控热点key，动态延长过期时间。

缓存雪崩（大量key同时过期 / Redis宕机，数据库压力暴增）

  • 事前：缓存过期时间增加随机偏移量，避免集体过期；部署Redis哨兵/集群，保证高可用。
  • 事中：服务端做限流与降级，非核心业务暂时关闭缓存、返回默认值；核心业务走熔断机制。
  • 事后：开启RDB+AOF持久化，Redis重启后快速恢复缓存数据。

4.2 Redisson分布式锁与WatchDog机制

原生setnx实现分布式锁存在无法自动续期、死锁、不可重入等问题，生产环境标准方案是Redisson分布式锁，核心是WatchDog（看门狗）自动续期机制。

  1. 核心原理

    • 获取锁成功后，Redisson会启动一个看门狗线程，默认锁的过期时间是30秒；
    • 每隔10秒（过期时间的1/3）检查一次，如果当前线程还持有锁，就重新将锁的过期时间重置为30秒，实现自动续期；
    • 业务代码执行完成后主动释放锁，或服务宕机后超时自动释放，避免死锁。

  2. 优势

    • 解决了业务执行时间超过锁过期时间导致的锁提前释放问题；
    • 支持可重入、公平锁、读写锁等多种锁模式；
    • 底层基于Lua脚本保证原子性，生产级稳定性。

五、Spring Boot Bean生命周期核心链路

Spring Boot启动流程无需全量背诵，核心抓住「Controller如何变成一个Bean」的主线：扫描 → 实例化 → 依赖注入 → 初始化 → 放入容器。

5.1 完整执行链路

  1. 组件扫描（Scan）
    启动类@SpringBootApplication注解包含@ComponentScan，启动时扫描指定包路径下所有带@Component及其衍生注解（@Controller、@Service、@Repository等）的类，将其解析为BeanDefinition（Bean的定义信息，包含类名、作用域、依赖关系等）。

  2. 实例化（Instantiation）
    Spring容器根据BeanDefinition，通过反射调用类的构造方法，创建出一个原始对象（此时属性还未赋值，是"半成品"）。

  3. 依赖注入（Dependency Injection）
    对实例化后的对象进行属性填充：

    • 解析@Autowired、@Resource等注解，从容器中找到对应的依赖Bean；
    • 通过反射给字段赋值（字段注入）、调用setter方法（setter注入）或构造方法传参（构造注入），完成依赖装配。

  4. 初始化（Initialization）
    执行Bean的初始化逻辑：

    • 执行Aware接口回调（如BeanNameAware、ApplicationContextAware）；
    • 执行BeanPostProcessor的前置处理；
    • 执行InitializingBean接口的afterPropertiesSet方法、或init-method指定的自定义初始化方法；
    • 执行BeanPostProcessor的后置处理 —— AOP动态代理就在此阶段生成。

  5. 存入单例池
    初始化完成后，完整的Bean对象被放入Spring容器的单例池中（一级缓存），成为可直接使用的Bean，供后续业务调用。

六、消息队列核心问题解决方案

任选RocketMQ或RabbitMQ深入，核心只抓两个问题：消息丢失怎么办、消息积压了怎么扩。

6.1 消息丢失的三端保障方案

从生产端、Broker存储端、消费端三个环节全程保障，避免消息丢失。

生产端

  • 发送确认机制：
    • RocketMQ：使用同步发送方式，等待Broker返回ACK确认；重要消息使用事务消息，保证本地事务与消息发送的一致性。
    • RabbitMQ：开启Publisher Confirm机制，Broker收到消息后回调确认。
  • 失败重试：发送失败后自动重试，重试次数与间隔可配置，多次失败后告警并落库人工处理。

Broker存储端

  • 持久化配置：
    • RocketMQ：配置同步刷盘（FlushDiskType=SYNC_FLUSH），确保消息写入磁盘后再返回ACK；
    • RabbitMQ：队列开启持久化、消息设置持久化属性，避免Broker重启丢失。
  • 集群高可用：部署主从集群/多副本，单节点故障不丢消息。

消费端

  • 手动ACK机制：关闭自动确认，业务逻辑真正执行完成后，再手动提交确认；
  • 失败重试 + 死信队列：消费失败的消息自动重试，达到最大重试次数后进入死信队列，避免阻塞正常消费，后续人工兜底处理。

6.2 消息积压的扩容与处理方案

  1. 第一步：定位积压根因
    先排查是消费速度慢（业务逻辑耗时久、下游接口超时），还是消费者实例不足，还是流量突增。优先修复消费逻辑瓶颈（如优化SQL、增加缓存、异步化）。

  2. 第二步：快速扩容消费能力

    • 横向扩容：增加消费者服务实例数量，提升并发消费能力；
    • 队列扩容：RocketMQ可增加Topic的队列数，让更多消费者线程并行消费；RabbitMQ可拆分队列，分散压力。

  3. 第三步：极端积压兜底
    若消息积压量极大，Broker即将撑满：

    • 临时转存：编写临时消费者，将积压消息批量转存到数据库/对象存储，先让Broker恢复正常；
    • 离线消费：后续再慢慢消费转存的历史消息，逐步补齐数据。

七、分库分表（ShardingSphere）核心三要点

7.1 基础配置方式

以ShardingSphere-JDBC为例，核心配置三步：

  1. 配置多数据源：声明多个数据库的连接信息；
  2. 配置分片规则：指定逻辑表、真实表的分布，配置分片键；
  3. 配置分片算法：选择按范围、按哈希取模等算法，定义数据路由规则。

示例（YAML配置片段）：

sharding:
  tables:
    t_order:
      actualDataNodes: ds${0..1}.t_order${0..3}
      databaseStrategy:
        mod:
          shardingColumn: user_id
          shardingAlgorithmName: db_mod
      tableStrategy:
        mod:
          shardingColumn: order_id
          shardingAlgorithmName: table_mod

7.2 分片键选择原则

分片键是分库分表的核心，选择直接决定查询性能，遵循以下原则：

  1. 高频查询维度：选择最常用的查询条件作为分片键，让大部分SQL都能路由到单库单表，避免跨片；
  2. 数据均匀分布：分片键的值分布要均匀，避免出现热点分片（某一个库/表数据量远大于其他）；
  3. 业务关联原则：关联表尽量使用相同分片键，比如订单表和订单明细表都用order_id分片，关联查询可路由到同分片。

7.3 跨分片查询兜底方案

跨分片查询性能差，优先从业务设计上避免，无法避免时按以下方案兜底：

  1. 二级索引方案：将查询条件与分片键的映射关系存入ES/Redis，先通过查询条件找到分片键，再路由到对应分片查询；
  2. 广播表：字典表、配置表等小表，设置为广播表，每个分片都存一份，避免跨库关联；
  3. 数据同步方案：将分库分表的数据同步到ES或数仓，复杂查询、报表查询直接走数仓，不碰分片库；
  4. 分页优化：跨分片分页查询禁止深分页，改用游标分页（按ID滚动），避免全分片扫描后归并。

八、业务系统设计方案

8.1 秒杀系统完整设计

围绕「流量怎么挡、库存怎么扣、订单怎么落、数据怎么拆」四层展开，逐层削峰，保护底层数据库。

1. 流量怎么挡：多层限流削峰

  • 前端层：按钮置灰、倒计时限制，减少重复点击；静态资源CDN加速。
  • 接入层：Nginx限流（按IP限流）、网关层令牌桶限流，拦截非法与超额流量。
  • 服务层：接口限流（Sentinel/Guava RateLimiter），按用户维度限流，防止刷单。
  • 核心思路：将流量层层过滤，最终落到数据库的流量只有原来的几十分之一。

2. 库存怎么扣：Redis预扣 + 数据库兜底

  • 库存预热：活动开始前，将商品库存同步到Redis中；
  • Redis预扣库存：使用Lua脚本原子执行「判断库存 → 扣减库存」操作，防止超卖，性能极高；
  • 数据库最终扣减：订单创建成功后，异步扣减数据库库存，以数据库库存为准，做最终一致性校验；
  • 库存回补：订单超时未支付，释放Redis库存与数据库库存。

3. 订单怎么落：异步下单 + 状态流转

  • 异步削峰：扣减Redis库存成功后，将下单信息发送到消息队列，不直接操作数据库；
  • 消费下单：消费者监听队列，批量生成订单，写入数据库；
  • 超时取消：使用延迟队列（RocketMQ延迟消息），订单超时未支付自动取消，回补库存。

4. 数据怎么拆：分库分表 + 冷热分离

  • 订单表按用户ID或订单ID分库分表，分散单表数据量；
  • 秒杀活动数据冷热分离，历史活动数据归档；
  • 热点商品数据单独缓存，与普通商品隔离。

8.2 消息分发平台设计

围绕「怎么接、怎么存、怎么推、失败怎么补、最终一致性、对账」六大核心点设计。

1. 海量消息怎么接

  • 接入层集群部署，水平扩展；
  • 接口限流与鉴权，防止非法请求；
  • 接收后直接写入消息队列暂存，异步处理，不直接落库，提升接入吞吐量。

2. 怎么存

  • 消息主体数据分库分表存储，按消息ID或接收时间分片；
  • 消息状态、推送记录单独存储，便于追溯；
  • 历史消息归档，冷热数据分离。

3. 怎么推

  • 多通道推送（短信、APP推送、邮件等），按优先级分级推送；
  • 批量推送机制，合并小批量请求，提升推送效率；
  • 推送链路异步化，解耦接收与推送。

4. 失败了怎么补

  • 重试机制：推送失败后自动重试，采用指数退避算法（间隔逐渐拉长），避免打爆下游；
  • 死信队列：达到最大重试次数仍失败的消息，进入死信队列，告警通知人工介入；
  • 降级兜底：某一推送通道故障时，自动切换到备用通道。

5. 最终一致性保障

  • 本地消息表方案：消息入库与业务操作在同一个本地事务中，保证消息不丢；
  • 事务消息：RocketMQ事务消息，保证业务执行与消息发送的原子性；
  • 状态机流转：消息全生命周期状态可追溯，每一步都有记录。

6. 对账怎么跑

  • 定时对账任务：T+1跑批，核对发送端、存储端、推送端三方数据；
  • 差异处理：对得上的标记成功，对不上的分类处理：漏发的补推，多发的标记异常；
  • 对账明细留存：所有对账结果与差异数据留存，便于审计与排查。
