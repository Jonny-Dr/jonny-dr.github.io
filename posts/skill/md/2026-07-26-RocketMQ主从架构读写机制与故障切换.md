# RocketMQ 核心设计思想 \+ 1主2从架构读写与故障切换专项文档

## 一、RocketMQ 精简核心设计思想

RocketMQ 整体设计目标：**兼顾金融级可靠性、高吞吐、海量消息堆积、业务原生能力，轻量化无中心架构，适配企业级微服务核心业务**。核心设计思想精简为以下五点，是其架构、读写、高可用机制的底层依据：

### 1\.1 读写分离存储设计（核心基石）

采用 **全局 CommitLog 顺序写 \+ 分区 ConsumeQueue 索引读** 架构。所有 Topic 消息统一顺序写入 CommitLog 保证超高磁盘写入性能，消费者仅读取轻量 ConsumeQueue 索引完成消费，读写彻底解耦，天然支持百万级消息堆积且不阻塞集群吞吐。

### 1\.2 分层高可用、性能与可靠性可动态取舍

NameServer 无状态集群消除路由单点；Broker 基于主从多副本实现高可用，提供**同步双写/异步复制、同步刷盘/异步刷盘**组合策略。核心业务通过强同步策略保障零数据丢失，非核心业务通过异步策略换取超高吞吐，灵活适配不同业务等级。

### 1\.3 企业级业务特性原生内置

相较于其他消息中间件，RocketMQ 内核原生集成顺序消息、事务消息、多级延迟消息、重试/死信队列、消息过滤等高频能力，无需业务侧额外开发组件，大幅降低分布式业务开发与运维成本。

### 1\.4 轻量化去中心化架构

无 Zookeeper 强依赖，NameServer 仅负责路由注册、心跳探测，不参与消息存储与转发。客户端自主拉取路由、自主负载均衡，架构极简、故障扩散范围小、运维成本低。

### 1\.5 全链路容错兜底设计

通过消费者组隔离、阶梯式重试、死信隔离、故障节点自动剔除、队列重分配等机制，在生产、存储、消费全链路实现容错，有效避免消息堆积、重复消费、业务雪崩等问题。

## 二、1主2从架构机制解读（无分片单Broker组）

本文基于生产常用轻量化架构：**单Broker分组、1 Master \+ 2 Slave、无多Master分片**，所有Topic队列归属同一Broker组，本节详细解读节点分工、读写核心机制。

### 2\.1 架构整体分工原则

**写流量独占主节点、读流量主从分担；从节点仅做数据副本与消费分流，无任何独立写入能力**，从根源保证消息写入的唯一性与有序性。

### 2\.2 消息写入机制（生产者）

集群中**仅Master节点处理所有写请求，两台Slave不接收任何生产者发送消息**，具体流程如下：

1. 生产者定时从 NameServer 拉取路由信息，所有写流量仅定向分发至 Master 节点；

2. Master 接收消息，落地写入本地 CommitLog，并生成 ConsumeQueue 索引文件；

3. 根据主从复制模式同步数据至从节点：
       

    - **异步复制**：Master 本地落盘成功即返回生产成功，后台异步线程同步数据至两台 Slave，存在未同步宕机丢失风险；

    - **同步双写**：必须等待两台 Slave 全部同步落地完成，才返回生产成功，实现多副本零丢失；

4. 延迟消息调度、事务消息处理、消息重试、死信写入、Topic配置变更等特殊写操作，仅Master节点支持。

### 2\.3 消息读取机制（消费者）

**Master、两台 Slave 均可承担消费读流量，实现读请求负载均衡**，最大化利用集群资源：

1. 两台 Slave 实时全量同步 Master 的 CommitLog、ConsumeQueue 数据，拥有完整消息副本；

2. 默认消费流量优先走 Master，当Master压力过高、消息堆积量大时，NameServer自动将读流量分摊至两台Slave；

3. 消费者从Slave拉取消息正常消费，有效分担Master读压力，提升集群整体吞吐。

### 2\.4 节点读写能力汇总表

|节点角色|消息写入（生产/特殊任务）|消息读取（消费拉取）|
|---|---|---|
|Master|全权负责，集群唯一可写节点|支持读取，优先承载消费流量|
|Slave1 / Slave2|禁止写入，仅被动同步主节点数据|支持读取，分担集群消费流量|

## 三、主从数据同步丢失问题详解

在1主2从架构的异步复制模式下，存在典型的数据丢失风险：**Master写入本地磁盘成功、未及时同步至两台Slave时突发宕机，该批次消息永久丢失**，本章独立解析问题根源、风险边界与完整解决方案。

### 3\.1 问题产生根源

异步复制（ASYNC\_MASTER）采用「先落盘、后同步」的机制：生产者发送消息后，只要Master将消息写入本地CommitLog磁盘，就立刻返回生产成功，无需等待Slave同步完成。若Master在此刻瞬间宕机、磁盘损坏，未同步的消息仅存在故障Master本地，集群无任何副本，无法恢复，最终造成消息永久丢失。

### 3\.2 风险边界界定

- **存在风险场景**：异步复制模式（搭配同步/异步刷盘），均存在未同步宕机消息丢失风险；

- **无风险场景**：同步双写架构（SYNC\_MASTER），消息必须同步复制到两台Slave并落地成功，才会返回生产成功，从架构层面彻底规避该问题。

### 3\.3 分级解决方案（根治\+业务兜底）

#### 3\.3\.1 架构根治方案（核心业务强制使用）

订单、支付、账务等零数据丢失核心业务，开启**同步双写\+同步刷盘**配置，强制三节点副本落地：

~~~
brokerRole=SYNC\_MASTER
flushDiskType=SYNC\_FLUSH
~~~

该方案牺牲少量吞吐性能，换取金融级数据可靠性，彻底杜绝主节点宕机未同步导致的消息丢失。

#### 3\.3\.2 业务兜底方案（非核心业务高吞吐适配）

日志、埋点、普通通知等可容忍极小数据丢失的业务，保留异步复制保证高吞吐，搭配业务层兜底机制：

- 消息预落库：发送消息前写入业务消息记录表，记录唯一msgId、业务单号、消息体、发送状态；

- 定时对账补偿：定时扫描「发送成功、消费未完成」的异常数据，自动补发消息；

- 消费幂等设计：适配消息重复补发场景，避免业务数据异常。

### 3\.4 故障应急处理原则

发生该故障时，**禁止重启故障Master**，防止新旧节点数据错乱、消息重复或缺失；优先晋升同步数据最全的Slave为新Master恢复业务写入，丢失消息仅可通过业务日志、对账任务补偿，MQ集群层面无法恢复。

## 四、主节点宕机故障切换机制

开源RocketMQ与商业版切换机制存在本质区别，开源原生无自动故障转移能力，仅商业版内置自动切换，本章详细说明宕机现象、手动切换流程、商业版切换原理。

### 4\.1 核心前置前提

**开源版原生RocketMQ不支持自动主从切换**，Master宕机后需人工介入恢复；仅阿里云等商业版自带自动故障转移能力。

### 4\.2 Master宕机后的集群表现

1. **生产服务完全中断**：集群无可用Master节点，生产者无法发送新消息；

2. **消费服务正常运行**：两台Slave数据完整，消费者可持续拉取存量消息消费，无消费中断；

3. 路由自动更新：Master默认120s心跳超时，NameServer自动剔除故障节点，不再分发流量。

### 4\.3 开源版手动切换标准流程

1. 锁定故障节点，禁止重启旧Master，避免集群数据不一致；

2. 选取数据同步偏移量最新的一台Slave，修改配置为Master角色；

3. 重启该节点，使其晋升为集群新Master；

4. 另一台Slave自动对接新Master，重建主从同步关系；

5. NameServer刷新路由信息，生产者恢复消息写入，集群恢复正常服务。

### 4\.4 商业版自动切换原理

商业版内置高可用管控组件，实现秒级无感知故障转移，流程如下：

1. 实时监控Master心跳、端口状态、主从数据同步位点；

2. 确认Master故障后，对比多台Slave偏移量，选举数据最完整的节点；

3. 自动修改节点角色配置、重启晋升新Master；

4. 刷新集群路由，业务短暂重试后自动恢复，无需人工介入。

### 4\.5 两种复制模式故障风险总结

- **异步复制**：切换前存在未同步消息丢失风险，依赖业务对账补偿；

- **同步双写**：所有消息均有多副本落地，主从切换零数据丢失，适配金融高可靠场景。

## 五、开源环境自定义自动主从切换方案

针对开源RocketMQ无原生自动切换的短板，生产环境可自研轻量化监控切换组件，实现Master故障后集群自愈，替代人工运维，适配1主2从架构。

### 5\.1 组件核心设计思路

整体逻辑：**常驻监控 \+ 精准故障判定 \+ 最优从节点选举 \+ 自动角色晋升 \+ 集群自愈 \+ 故障告警**，全程无人干预，实现故障自动转移。

### 5\.2 组件核心能力

- **多维度心跳探测**：定时请求NameServer路由、探测Broker端口、校验节点心跳，精准区分节点宕机与网络抖动、假死；

- **同步位点择优选举**：实时采集两台Slave的CommitLog最大偏移量，优先选择数据最全的从节点晋升，最大限度减少数据丢失；

- **防误判保护机制**：采用多次连续探测失败判定故障，规避短暂网络超时引发的误切换，保障集群稳定；

- **自动配置变更与重启**：远程修改备选Slave的brokerRole角色配置，自动重启完成Master晋升；

- **集群自动自愈**：新Master启动后，自动联动另一台Slave重建主从同步，刷新NameServer路由，恢复完整读写服务；

- **日志留存与告警**：切换全程记录运维日志，触发短信/邮件告警，便于故障复盘。

### 5\.3 完整执行流程

1. 监控服务常驻运行，定时轮询采集1主2从所有节点状态、数据同步位点；

2. 连续探测确认Master心跳超时、端口不可达，判定节点真实故障；

3. 对比两台Slave数据偏移量，选举数据最全节点作为备选新Master；

4. 自动修改节点角色配置、重启节点，完成主从切换晋升；

5. 集群路由更新，生产、消费客户端自动重连新Master，业务恢复正常；

6. 触发故障告警，留存切换日志与数据位点信息。

### 5\.4 落地优势与注意事项

**落地优势**：完全适配开源免费版本，无需依赖商业组件，解决Master宕机后生产长期中断问题，实现集群自愈，大幅降低运维成本与故障时长。

**核心注意事项**：异步复制模式下，自动切换仍存在少量未同步消息丢失风险；核心业务必须搭配同步双写架构，才能彻底保障数据零丢失。

### 5\.5 落地方案实现流程（脚本\+定时任务全流程实操）

针对开源RocketMQ无自动主从切换能力，本节提供**可直接落地的自研自动化切换方案**，通过「常驻定时监控脚本 \+ 故障判定逻辑 \+ 配置热修改 \+ 节点重启自愈」实现1主2从架构故障自动切换，无需人工介入。

#### 5\.5\.1 整体部署架构

单独部署一台运维监控机器（或任意集群节点），部署Python/Shell监控脚本，通过Linux Crontab常驻定时任务，轮询监控RocketMQ Master节点状态与双从节点同步位点，全程无侵入、轻量化运行。

#### 5\.5\.2 核心监控定时任务配置

采用Crontab秒级轮询机制，每10秒执行一次健康探测，兼顾实时性与系统负载，配置如下：

`*/10 * * * * /usr/local/rocketmq-monitor/switch-monitor.sh >> /usr/local/rocketmq-monitor/monitor-log.log 2&>1`

任务作用：常驻巡检集群状态，探测Master存活、采集双从节点数据偏移量，异常时触发故障切换流程。

#### 5\.5\.3 监控脚本核心执行逻辑（可直接落地）

脚本分为四层核心逻辑：节点存活探测、防误判防抖、从节点位点比对、自动切换自愈。

**第一步：Master节点健康探测**

脚本通过两种方式双重校验Master状态，规避网络抖动误判：1、端口探测9876/10911服务端口是否通畅；2、调用NameServer路由接口，校验Master节点是否在线。连续3次探测失败（共计30秒）判定为真实宕机，排除瞬时网络超时、进程假死场景。

**第二步：双从节点数据位点采集与最优选举**

脚本调用Broker状态查询命令，实时获取两台Slave节点的CommitLog最大偏移量，对比两者数据同步进度：优先选择**偏移量最大、数据最完整**的Slave作为新任Master，最大限度减少数据缺失。同时记录故障瞬间位点信息，用于后续故障复盘与数据补偿。

**第三步：故障锁定防重复切换**

脚本内置故障锁文件机制，一旦触发切换，生成lock锁定文件，锁定期间不再重复执行切换逻辑，避免节点未完全重启、集群未稳定时，重复触发切换导致集群震荡。集群恢复稳定后自动释放锁文件。

**第四步：自动主从角色切换操作**

1、远程登录最优Slave节点，修改broker\.conf配置文件，将 `brokerRole=SLAVE` 修改为 `brokerRole=SYNC_MASTER/ASYNC_MASTER`；
2、执行Broker优雅停机与重启命令，完成新Master晋升；
3、自动修改另一台Slave节点配置，保持从节点角色，自动对接新Master重建主从同步；
4、清空旧Master故障路由缓存，主动刷新NameServer集群路由信息。

**第五步：集群自愈与业务恢复**

新Master启动成功后，脚本自动校验节点读写可用性，确认集群恢复1主1从/1主2从正常架构。生产消费者客户端通过定时拉取路由，自动感知新Master节点，恢复消息写入与消费，业务自动自愈。

**第六步：日志留存与告警推送**

全程记录切换时间、故障节点、新主节点、数据偏移量、操作日志；切换完成后自动推送短信/钉钉/邮件告警，通知运维人员故障事件，便于人工复盘核对数据。

#### 5\.5\.4 切换后兜底校验机制

1、切换完成后休眠60秒，巡检集群同步状态，确认主从同步正常、无数据错位；
2、校验生产写入、消费拉取功能是否正常，异常则触发二次告警；
3、异步复制模式下，自动生成缺失数据位点日志，为业务对账补偿提供依据。

#### 5\.5\.5 脚本落地核心约束与规范

1、所有操作采用**优雅启停**，禁止强制kill进程，避免文件损坏、日志错乱；
2、仅故障Master宕机场景触发切换，正常节点重启、运维操作不会触发；
3、全程无人工干预，轻量化脚本运行，不占用MQ集群性能资源；
4、核心金融业务需配合同步双写架构，脚本自愈仅解决服务中断问题，无法彻底规避异步模式数据丢失风险。

#### 5\.5\.6 自动化切换 Shell 脚本完整示例（可直接落地）

本脚本适配 RocketMQ 1主2从架构，完整实现**节点探测、故障防抖、位点比对、自动晋升、集群自愈、日志告警、防重复切换**能力，配合前文10秒定时任务可实现生产级自动故障转移。

```bash
    echo "[$DATE_NOW] $1" >> $LOG_PATH
}

#################### 4. 防重切换锁判断 ####################
if [ -f $LOCK_FILE ];then
    log "检测到切换锁定文件，本次跳过巡检"
    exit 0
fi

#################### 5. Master存活探测 ####################
check_master_alive(){
    # 端口探测 + 路由双重校验
    nc -z $MASTER_IP 10911
    if [ $? -eq 0 ];then
        return 0
    else
        return 1
    fi
}

#################### 6. 获取Slave节点CommitLog偏移量 ####################
get_slave_offset(){
    # 调用mqadmin获取节点最大偏移量
    OFFSET=$(sh /usr/local/rocketmq/bin/mqadmin brokerStatus -n $NAMESERVER_ADDR -b $1:10911 | grep "maxOffset" | awk '{print $2}')
    echo $OFFSET
}

#################### 7. 主从自动切换核心逻辑 ####################
switch_master(){
    # 创建锁文件，禁止重复切换
    touch $LOCK_FILE
    log "========== 检测到Master故障，开始执行自动切换 =========="

    # 1. 获取两台从节点数据偏移量
    SLAVE1_OFFSET=$(get_slave_offset $SLAVE1_IP)
    SLAVE2_OFFSET=$(get_slave_offset $SLAVE2_IP)
    log "Slave1偏移量：$SLAVE1_OFFSET , Slave2偏移量：$SLAVE2_OFFSET"

    # 2. 选举数据最全节点为新Master
    if [ $SLAVE1_OFFSET -ge $SLAVE2_OFFSET ];then
        NEW_MASTER=$SLAVE1_IP
        BACKUP_SLAVE=$SLAVE2_IP
    else
        NEW_MASTER=$SLAVE2_IP
        BACKUP_SLAVE=$SLAVE1_IP
    fi
    log "选举新Master节点：$NEW_MASTER"

    # 3. 远程修改新Master配置，晋升为主节点
    ssh $NEW_MASTER "sed -i 's/brokerRole=SLAVE/brokerRole=ASYNC_MASTER/g' $BROKER_CONF"
    # 优雅重启Broker
    ssh $NEW_MASTER "sh /usr/local/rocketmq/bin/mqshutdown broker && sh /usr/local/rocketmq/bin/mqstart broker -d"
    log "新Master $NEW_MASTER 晋升重启完成"

    # 4. 备用从节点保持从角色，自动同步新主
    ssh $BACKUP_SLAVE "sed -i 's/brokerRole=MASTER/brokerRole=SLAVE/g' $BROKER_CONF"

    # 5. 刷新路由、释放锁（60秒后自愈）
    sleep 60
    rm -f $LOCK_FILE
    log "========== 自动切换完成，集群恢复自愈 =========="
    
    # 可在此处接入钉钉/邮件告警脚本
}

#################### 8. 主流程防抖巡检 ####################
if ! check_master_alive;then
    FAIL_COUNT=$((FAIL_COUNT+1))
    log "Master节点探测失败，当前失败次数：$FAIL_COUNT"
    if [ $FAIL_COUNT -ge $FAIL_COUNT_MAX ];then
        switch_master
    fi
else
    # 节点正常，重置失败计数
    FAIL_COUNT=0
fi

exit 0

```

#### 5\.5\.7 脚本使用说明

**1、部署步骤**

1\. 创建监控目录：`mkdir -p /usr/local/rocketmq-monitor`；
2\. 将脚本保存为 `switch-monitor.sh`，赋予执行权限：`chmod +x switch-monitor.sh`；
3\. 修改脚本内集群IP、路径、环境参数为现场实际配置；
4\. 配置前文10秒crontab定时任务，常驻巡检。

**2、脚本核心特性**

支持故障防抖、锁文件防重复切换、按数据偏移量择优选举、优雅启停不损坏日志、全程日志溯源，完全适配自研自动切换落地方案。

**3、扩展优化点**

可对接钉钉/企业微信机器人接口，实现切换故障实时告警；可增加切换后读写可用性校验，异常自动二次告警。

## 六、整体总结

本文基于RocketMQ轻量化、高可用、可适配的核心设计思想，围绕企业常用的**1主2从无分片Broker架构**，完整梳理了读写机制、数据同步风险、故障切换能力与自定义自愈方案。架构层面采用写主读从的分工模式，兼顾写入稳定性与消费负载能力；异步复制存在主节点宕机未同步消息丢失缺陷，核心业务需通过同步双写架构兜底，非核心业务依赖业务对账补偿；开源版本无原生自动切换能力，可通过自研监控组件实现故障自动自愈，有效解决生产故障人工介入、服务中断时间长的问题。整套架构轻量化、运维简单、性能与可靠性可灵活取舍，非常适配中小规模稳定型核心业务系统。
