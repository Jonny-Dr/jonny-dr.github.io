# Java 内存模型（JMM）完全解读
> 从「为什么需要 JMM」到「8 大原子操作」，再到 volatile / synchronized / final 的内存语义，一次讲透。
> 主线：**可见性 · 有序性 · 原子性** —— 这三座大山，就是 JMM 全部规则存在的理由。

---

## 序章：先破除三个最流行的误解

在展开之前，必须先拆掉三堵墙，否则后面全是白听。

| 常见误解 | 真相 |
| --- | --- |
| ❌ JMM 就是 JVM 的堆、栈、方法区 | **完全两回事**。堆/栈/方法区是「JVM 运行时数据区」，描述内存怎么划分；JMM 是「并发读写共享变量的**行为规范**」，描述线程之间怎么看见彼此的写。前者管**放哪**，后者管**怎么看**。 |
| ❌ 主内存就是内存条，工作内存就是 CPU 缓存 | **不对**。它们是 JMM 为了跨平台而造出来的**抽象概念**，可大致对应到「内存条 + 寄存器/缓存」，但 JMM 刻意不绑定任何具体硬件——这样同一套规则既能跑在 x86 上，也能跑在 ARM 上。 |
| ❌ JMM 是一个真实的内存结构 | **不是**。它是一组**规则/契约**（JSR-133 定义）：只要你按它的规则写并发代码，JVM 就必须保证你得到它承诺的结果。 |

> **一句话定性：JMM 是 Java 语言级别的「内存可见性与顺序」规范，它屏蔽硬件差异，告诉程序员"什么情况下一个线程的写，一定能被另一个线程看到"。**

---

## 第一章：JMM 因何而生 —— 并发的三大源头问题

JMM 不是拍脑袋想出来的，它是被三个硬件/编译器层面的"优化原罪"逼出来的。

### 1.1 源头一：CPU 缓存 → 可见性问题

现代 CPU 的速度和内存条的速度差了两个数量级。为了填补这个鸿沟，硬件引入了多级缓存：

```
CPU 核心 → L1 缓存 → L2 缓存 → L3 缓存（多核共享） → 主内存
            ↑ 每核私有                        ↑ 所有核共享
```

**后果**：线程 A 在 CPU-1 上改了变量 `x`，新值可能只躺在 CPU-1 的 L1 缓存里，还没刷回主内存；线程 B 在 CPU-2 上读 `x`，拿到的是自己缓存里的**旧值**。这就是**可见性问题**——一个线程改了，另一个线程看不见。

```java
static boolean running = true;   // 普通变量，无 volatile

// 线程 B
while (running) { /* 空转 */ }
System.out.println("B 结束");     // 可能永远执行不到

// 线程 A（1 秒后）
running = false;                  // B 可能永远看不到！
```

### 1.2 源头二：重排序 → 有序性问题

为了跑得更快，至少有三层角色会**打乱你写的代码顺序**：

| 重排序来源 | 谁干的 | 说明 |
| --- | --- | --- |
| 编译器重排序 | javac / JIT | 编译器认为调整指令顺序不改变单线程语义，就调了 |
| 指令级并行重排序 | CPU | 现代 CPU 乱序发射，多条指令并行执行 |
| 内存系统重排序 | 缓存 / 写缓冲 | 由于写缓冲区存在，读到的可能是"陈旧"的缓存值，看起来像执行顺序被打乱 |

**后果**：代码写的是 `a = 1; flag = true;`，另一个线程可能先看到 `flag == true`，再看到 `a == 1`（甚至看不到）。这就是**有序性问题**。

### 1.3 源头三：线程切换 + 非原子操作 → 原子性问题

即使看起来天经地义的一行 `i++`，在字节码层面都是**三步**：

```
1. 读取 i 的值到操作数栈        （read + load + use）
2. 加 1                        （CPU 计算）
3. 写回 i                      （assign + store + write）
```

线程在这三步之间随时可能被 OS 挂起。两个线程同时 `i++`，各读到 0，各算出 1，各写回 1 —— 两次自增，结果只加了 1。这就是**原子性问题**。

> **可见性、有序性、原子性 —— 这"并发三座大山"就是 JMM 要解决的问题。** 记住这条主线，后面所有规则都围绕它们展开。

## 第二章：JMM 的抽象世界 —— 主内存与工作内存

### 2.1 抽象结构全景

```
   ┌──────────────────────┐              ┌──────────────────────┐
   │      线程 A           │              │      线程 B           │
   │  ┌────────────────┐  │              │  ┌────────────────┐  │
   │  │  CPU 执行引擎   │  │              │  │  CPU 执行引擎   │  │
   │  └───▲────────┬───┘  │              │  └───▲────────┬───┘  │
   │   use│        │assign│              │   use│        │assign│
   │  ┌───┴────────▼───┐  │              │  ┌───┴────────▼───┐  │
   │  │  工作内存 A     │  │              │  │  工作内存 B     │  │
   │  │  变量副本 x',y' │  │              │  │  变量副本 x',y' │  │
   │  └───▲────────┬───┘  │              │  └───▲────────┬───┘  │
   └──────┼────────┼──────┘              └──────┼────────┼──────┘
      read│        │store/write             read│        │store/write
       load        ▼                        load         ▼
   ┌────────────────────────────────────────────────────────────┐
   │            主内存 Main Memory（所有线程共享）                  │
   │            共享变量：x, y, sharedObj ...                     │
   └────────────────────────────────────────────────────────────┘
```

### 2.2 两条铁律

1. **线程不能直接读写主内存**，所有操作必须经过自己的工作内存：先拷贝副本 → 操作副本 → 再刷回。
2. **工作内存之间完全隔离**，线程 A 看不到线程 B 的工作内存。线程间通信**只能**通过主内存这个"中转站"。

> ⚠️ **关键澄清：工作内存是抽象概念**，它实际对应 CPU 寄存器 + L1/L2 缓存 + 写缓冲区的一个**逻辑合集**。不要在硬件里找"哪个盒子是工作内存"。

### 2.3 哪些变量住在主内存（重点）

| 住在主内存（共享，有并发风险） | 不在主内存（线程私有，天然安全） |
| --- | --- |
| 实例字段（对象成员变量） | 局部变量 |
| 静态字段（static） | 方法参数 |
| 数组元素 | 异常处理参数 |

**这就是为什么局部变量永远不会有线程安全问题** —— 它压根不在共享内存里，每个线程自己栈里一份。

### 2.4 八大原子操作：主内存与工作内存的唯一交互方式

主内存与工作内存之间，只能靠这 8 个不可分割的操作交互：

| 操作 | 作用域 | 含义 | 关键约束 |
| --- | --- | --- | --- |
| `lock` | 主内存 | 把变量标记为线程独占 | 加锁后**清空**该变量在工作内存的副本，用前必须重新 load |
| `unlock` | 主内存 | 释放独占 | 必须在 `write` **完成之后**才能解锁 |
| `read` | 主内存 | 从主内存读出值，传给工作内存 | 与 `load` **必须成对顺序出现** |
| `load` | 工作内存 | 把 read 来的值放入变量副本 | 同上 |
| `use` | 工作内存 | 把副本值交给 CPU 执行引擎 | 变量必须先 read+load 才能 use |
| `assign` | 工作内存 | 把 CPU 计算结果写回副本 | 赋值操作必须执行 assign |
| `store` | 工作内存 | 把副本值传出去，准备写主内存 | 与 `write` **必须成对顺序出现** |
| `write` | 主内存 | 把 store 来的值写入主内存变量 | 同上 |

#### 🔒 锁相关（synchronized 使用，volatile 不涉及）

**`lock`（主内存）**：锁定主内存变量，标记为当前线程独占。

> 约束：加锁后**清空**当前线程工作内存中该变量的副本，使用变量前必须重新 `load`。

**`unlock`（主内存）**：解锁主内存变量，释放独占，其他线程可竞争锁。

> 约束：
> - 加锁后必须解锁；解锁前必须先加锁（同一线程可重入 lock 多次，unlock 次数必须相同）
> - `write` 完成之后才能解锁

#### 📥 读取链路：主内存 → 工作内存 → CPU（read → load → use）

- **`read`（主内存）**：从主内存读取变量值，传递给工作内存。
  
  > 约束：`read` 和 `load` **必须成对顺序出现**（不允许 read 而无 load）
- **`load`（工作内存）**：把 read 拿到的值，加载到线程工作内存的变量副本。
- **`use`（工作内存）**：将工作内存变量的值传递给 CPU 执行引擎，用于计算。

#### 📤 写入链路：CPU → 工作内存 → 主内存（assign → store → write）

- **`assign`（工作内存）**：CPU 计算完成，将结果写回工作内存变量副本。
  
  > 约束：赋值操作必须执行 `assign`；且 assign 之后必须同步回主内存（store + write）
- **`store`（工作内存）**：把工作内存变量的值传递出去，准备写入主内存。
  
  > 约束：`store` 和 `write` **必须成对顺序出现**（不允许 store 而无 write）
- **`write`（主内存）**：将 store 传递的值，写入主内存共享变量。

### 2.5 三条完整数据流（记忆主干）

**① 读链路：主内存 → 线程 CPU**
`read`（读主存）→ `load`（加载到工作内存）→ `use`（交给 CPU 运算）

> read 与 load 必须成对连续执行

**② 写链路：CPU → 主内存**
CPU 运算 → `assign`（更新工作内存副本）→ `store`（传递数据）→ `write`（写入主存）

> store 与 write 必须成对连续执行

**③ synchronized 锁链路**
`lock` 锁定主内存变量 → **清空工作内存副本** → read+load 加载最新值 → use 运算 → assign 修改副本 → store+write 刷入主内存 → `unlock` 解锁

> unlock 前必须完成 write，保证修改对其他线程可见

### 2.6 约束规则汇总

1. `lock` 与 `unlock` 成对：加锁必解锁，解锁前必须加锁
2. `lock` 后清空工作内存副本，使用变量前必须重新 `load`
3. `unlock` 前必须完成 `write`，数据刷入主内存才能解锁
4. `read` 和 `load` 必须成对顺序出现
5. `store` 和 `write` 必须成对顺序出现
6. CPU 赋值运算，必须执行 `assign` 写回工作内存
7. 变量只能诞生于主内存：`use` / `store` 之前，必须先经过 `read`+`load` / `assign`
8. 未被 `assign` 过的变量，不允许 `store` 回主内存

> 📌 **注**：8 个原子操作是 JMM 的**经典教学表述**（源自 JSR-133 之前的定义方式）。JSR-133 之后，JMM 的正式定义改用 **happens-before 规则**（第四章）描述，8 个操作退化为"帮助理解"的模型。但要知道它和 happens-before 是**同一件事的两种说法**：8 个操作描述"数据怎么搬"，happens-before 描述"结果什么时候可见"。

## 第三章：重排序 —— JMM 的头号对手

### 3.1 数据依赖性

如果两个操作访问**同一个变量**，且其中**至少一个是写操作**，那它们之间有数据依赖。编译器和 CPU **不会**重排有数据依赖的操作（否则单线程语义会被破坏）。

```java
a = 1;  b = a;   // 写后读（RAW）：不能重排
a = 1;  a = 2;   // 写后写（WAW）：不能重排
b = a;  a = 1;   // 读后写（WAR）：不能重排
```

**但是** —— 如果操作之间**没有**数据依赖（比如访问不同变量），重排序就完全合法：

```java
int a = 1;        // ①
int b = 2;        // ② ← 与 ① 无依赖，可重排
boolean f = true; // ③ ← 与 ①② 无依赖，可重排
```

单线程里这无所谓，但**多线程里，另一个线程可能正在观察这些操作的顺序** —— 灾难就此产生。

### 3.2 as-if-serial 语义

这是给**单线程**的承诺：

> **不管编译器和 CPU 怎么重排序，单线程程序的执行结果不能被改变。**

所以你在单线程里永远察觉不到重排序。但也正因为 as-if-serial **只保护单线程**，多线程下它是失效的 —— 这正是 JMM 必须额外提供 happens-before 的原因。

### 3.3 重排序如何在多线程下"犯罪"

```java
// 线程 A
a = 1;          // ①
flag = true;    // ②

// 线程 B
if (flag) {        // ③ 读到 true
    int r = a;     // ④ r 可能是 0！不是 1
}
```

①②无数据依赖 → 可能被重排成 ②① → 线程 B 在 ③ 看到 `flag=true`，但 ④ 读 `a` 时 ① 还没执行，拿到 0。**这就是有序性问题的现场。**

## 第四章：happens-before —— JMM 的灵魂

这是 JMM 中最重要、也最容易被误读的概念。

### 4.1 定义（务必咬文嚼字）

> **如果操作 A happens-before 操作 B，那么 A 的执行结果必须对 B 可见，且 A 的执行顺序排在 B 之前。**

三个致命细节：

1. **happens-before ≠ 时间上的先后**。A 在时间上先发生，不代表 A hb B；反过来，**A hb B 也不意味着时间上 A 一定先跑**（只要结果正确，JVM 可以自由重排）。
2. 它是 JMM 对**程序员的承诺**：你只要能推导出 A hb B，JVM 就担保 B 能看到 A 的结果，**不管底层怎么重排序**。
3. 它是**可以传递**的：A hb B，B hb C ⟹ A hb C。

### 4.2 happens-before 八条规则

| # | 规则 | 含义 | 代码形态 |
| --- | --- | --- | --- |
| 1 | **程序顺序规则** | 同一线程内，前面的操作 hb 后面的操作 | `a=1; b=2;` ⟹ `a=1` hb `b=2` |
| 2 | **监视器锁规则** | 对同一个锁，**unlock** hb 后续的 **lock** | 线程 A 在 synchronized 块里的写，线程 B 进块后必看到 |
| 3 | **volatile 变量规则** | 对同一个 volatile 变量，**写** hb 后续的 **读** | volatile 可见性的理论依据 |
| 4 | **线程启动规则** | `Thread.start()` hb 该线程的任何操作 | 主线程 start 前的写，子线程全看得到 |
| 5 | **线程终止规则** | 线程内所有操作 hb 其他线程检测到它终止 | `t.join()` 返回后，t 里所有写都可见 |
| 6 | **线程中断规则** | `interrupt()` hb 被中断线程检测到中断 | — |
| 7 | **对象终结规则** | 对象构造函数结束 hb `finalize()` 开始 | — |
| 8 | **传递性** | A hb B，B hb C ⟹ A hb C | 把上面所有规则串起来的胶水 |

### 4.3 用 happens-before 修复 3.3 的"犯罪现场"

只要把 `flag` 声明为 `volatile`：

```java
volatile boolean flag = false;
int a = 0;

// 线程 A
a = 1;          // ①
flag = true;    // ② volatile 写

// 线程 B
if (flag) {        // ③ volatile 读
    int r = a;     // ④ 一定是 1
}
```

推导链：

- ① hb ②（规则 1：程序顺序）
- ② hb ③（规则 3：volatile 写 hb 后续 volatile 读）
- ③ hb ④（规则 1：程序顺序）
- ⟹ **① hb ④**（规则 8：传递性）

所以 `a=1` 一定对 ④ 可见。同时 volatile 还会**禁止** ① 和 ② 的重排序（见第五章），双保险。

### 4.4 JMM 的设计智慧（重点）

JMM 采取了非常聪明的**双层策略**：

- **对程序员（上层）**：用 happens-before 给出强承诺 —— 只要能推导出 hb 关系，结果就正确。程序员不需要懂内存屏障。
- **对编译器和 CPU（下层）**：**能放开就尽量放开**。只要不破坏 hb 关系，想怎么重排序、怎么优化都行。

这就是为什么 Java 既能保证正确性，又能保持高性能。JMM 追求的不是"禁止一切优化"，而是"**在不改变程序执行结果的前提下，尽可能放开对编译器和处理器的限制**"。

## 第五章：volatile 深度解剖

### 5.1 volatile 在这套模型中的位置

回到八大原子操作的视角：**volatile 不使用 lock/unlock，它是对 read/load/use/assign/store/write 这 6 个操作的"指令重排与时机"做限制。**

| 维度 | volatile 的表现 |
| --- | --- |
| 可见性 | 强制 `store`/`write` 立刻刷入主内存；读取时强制 `read`/`load`，不用工作内存旧副本 |
| 有序性 | 通过内存屏障，限制 JVM/CPU 不能随意打乱相关 load、store 指令顺序 |
| 原子性 | ❌ 没有 `lock`/`unlock`，无法保证复合操作（如 `i++`）原子性 |

### 5.2 可见性的实现

- **写**一个 volatile 变量：JMM 强制把该线程工作内存里的**所有共享变量副本**立刻 `store + write` 刷回主内存；
- **读**一个 volatile 变量：JMM 强制该线程**重新 `read + load`** 主内存最新值，丢弃工作内存里的旧副本。

> 注意是"所有共享变量"，不只是 volatile 那个 —— 这也是 4.3 里普通变量 `a` 能被看到的深层原因之一。

### 5.3 禁止重排序：内存屏障（Memory Barrier）

JMM 定义了 4 种屏障，插在 volatile 读写的前后：

| 屏障 | 作用 |
| --- | --- |
| `StoreStore` | 禁止前面的普通写 与 后面的 volatile 写 重排序 |
| `StoreLoad` | 禁止前面的 volatile 写 与 后面的 volatile 读/写 重排序（**开销最大**，也最关键） |
| `LoadLoad` | 禁止前面的 volatile 读 与 后面的普通读 重排序 |
| `LoadStore` | 禁止前面的 volatile 读 与 后面的普通写 重排序 |

**插入策略：**

```
volatile 写操作：
    StoreStore 屏障          ← 前面所有普通写必须先刷回主存
    [ volatile 写 ]
    StoreLoad  屏障          ← 防止 volatile 写与后续 volatile 读重排

volatile 读操作：
    [ volatile 读 ]
    LoadLoad   屏障          ← 防止后面的普通读被提前
    LoadStore  屏障          ← 防止后面的普通写被提前
```

**底层实现**：在 x86 上，volatile 写通过一条带 **`lock` 前缀**的指令实现（如 `lock addl $0x0,(%rsp)`）。它会：

1. 触发 CPU 缓存一致性协议（MESI），把修改**立即写回主内存**，并**失效其他 CPU 的缓存行**；
2. 充当内存屏障，阻止前后指令重排。

### 5.4 为什么 volatile 不保证原子性（重点）

因为它**缺少 lock/unlock**。看 `i++` 的拆解：

```java
volatile int i = 0;   // 加 volatile 也没用

// 线程 A 和 B 同时执行 i++，各 10000 次
// 结果几乎必然 < 20000
```

`i++` = 读 → 改 → 写 三步。volatile 只保证：

- 读的时候拿到最新值（可见性 ✅）
- 写的时候立刻刷回（可见性 ✅）
- 这三步不被内部重排（有序性 ✅）

但它**没法把这三步"捆成一个不可分割的整体"**。线程 A 读到 i=5，还没来得及加 1 写回，线程 B 也读到 i=5 —— 两个都算出 6，写回 6。**原子性 ❌**。

> 要原子性，请用 `synchronized`、`Lock`，或 `AtomicInteger`（CAS）。

### 5.5 volatile 的正确使用场景

✅ **状态标志位**（最经典）

```java
volatile boolean shutdown = false;
void shutdown() { shutdown = true; }
void doWork()   { while (!shutdown) { /* ... */ } }
```

✅ **双重检查锁定（DCL）单例** —— 见 5.6

✅ **独立观察 / 一次性发布**

```java
volatile Config config;
void init() { config = new Config(...); }   // 安全发布给其他线程
```

❌ **不适合**：`i++` 类复合操作、依赖多个变量的不变式（volatile 救不了 `lower < upper` 这种跨变量约束）。

### 5.6 重点王炸：DCL 单例为什么必须加 volatile

```java
public class Singleton {
    private static volatile Singleton instance;   // ← 这个 volatile 不能省！

    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二次检查
                    instance = new Singleton();    // ← 问题出在这行
                }
            }
        }
        return instance;
    }
}
```

`instance = new Singleton()` 看起来是原子的，实际分三步：

```
1. memory = allocate();        // 分配对象内存空间
2. ctorInstance(memory);       // 初始化对象（调构造函数）
3. instance = memory;          // 把引用指向这块内存
```

**第 2 步和第 3 步没有数据依赖，JIT 可以重排成 1→3→2！**

于是：线程 A 执行到 ③（引用已赋值，但对象还没初始化），线程 B 此时调用 `getInstance()`，第一次检查发现 `instance != null`，**直接返回一个尚未初始化的半成品对象** → 崩溃或行为异常。

**加上 volatile 后**：`StoreStore` 屏障禁止"对象初始化（普通写）"被重排到"volatile 写（引用赋值）"之后，1→2→3 的顺序被锁死。

## 第六章：锁（synchronized）的内存语义

### 6.1 synchronized 的三重保证

`synchronized` 是 JMM 里唯一能**同时**保证三性的原生机制：

| 特性 | synchronized 如何保证 |
| --- | --- |
| **原子性** | `monitorenter` / `monitorexit` 之间的代码互斥，同一时刻只有一个线程执行 |
| **可见性** | **unlock 前必须把变量同步回主内存**（对应八大操作：`write` 完成后才能 `unlock`）；**lock 时会清空工作内存副本**，用前必须重新 `read + load` |
| **有序性** | 一个变量同一时刻只允许一个线程 `lock`，相当于把并发执行"拉直"成串行，天然有序 |

### 6.2 锁的内存语义 ≡ volatile 的内存语义（重点）

| | volatile | 锁 |
| --- | --- | --- |
| **写 / 释放** | volatile **写** → 立刻刷回主内存 | **释放锁**（unlock）→ 立刻刷回主内存 |
| **读 / 获取** | volatile **读** → 重新从主内存加载 | **获取锁**（lock）→ 清空副本，重新加载 |

> **结论：`锁的释放-获取` 与 `volatile 的写-读` 具有完全相同的内存语义。**
>
> - 线程 A 释放锁 hb 线程 B 获取同一个锁（happens-before 规则 2）
> - volatile 写 hb volatile 读（happens-before 规则 3）
>
> `ReentrantLock` 这类 AQS 实现的锁，其内存语义正是靠内部一个 `volatile int state` 达成的 —— **用 volatile 的 happens-before 撑起了锁的可见性**。

## 第七章：final 字段的内存语义

`final` 不只是"不可改"，它在 JMM 里也有**明确的重排序规则**，保证你拿到 final 字段时一定是正确初始化的值。

### 7.1 两条规则

**规则一（写 final 域）**：在构造函数里对一个 final 域的写入，与随后把这个被构造对象的引用赋值给一个引用变量，**这两个操作不能重排序**。

```java
class Holder {
    final int x;
    int y;
    static Holder obj;

    public Holder() {
        x = 1;     // ① 写 final 域
        y = 2;     // ② 写普通域
    }

    public static void writer() {
        obj = new Holder();   // ③ 发布引用
    }
}
```

① 不会被重排到 ③ 之后 ⟹ 其他线程只要看到 `obj != null`，**保证读到 `x == 1`**。
但 ②（普通域 y）可能被重排到 ③ 之后 ⟹ 其他线程**可能读到 `y == 0`**。

**规则二（读 final 域）**：初次读一个含 final 域对象的**引用**，与随后初次读这个 **final 域**，这两个操作不能重排序。

### 7.2 ⚠️ 逃逸陷阱：final 也救不了 this 逃逸

```java
class Holder {
    final int x;
    static Holder obj;

    public Holder() {
        x = 1;
        obj = this;   // ❌ 在构造函数里把 this 发布出去！
    }
}
```

即使在构造函数最后一行发布 `this`，其他线程也可能看到一个 `x` 还没初始化的对象。**final 的规则只保证"构造函数正常结束后"的安全发布，救不了构造函数内部的 this 逃逸。**

> 这也解释了为什么 DCL 单例的引用赋值不能夹在构造逻辑中间。

## 第八章：三大特性的终极保障总表

| 特性 | 问题来源 | 保障手段 | 关键机制 |
| --- | --- | --- | --- |
| **可见性** | CPU 缓存导致的工作内存副本陈旧 | `volatile` / `synchronized` / `final` / `Lock` | volatile 强制 store/write + read/load；锁的 lock 清空副本、unlock 前 write；final 的发布规则 |
| **有序性** | 编译器 + CPU + 内存系统三重重排序 | `volatile` / `synchronized` / `Lock` | 内存屏障（volatile）；happens-before 规则；锁的互斥串行化 |
| **原子性** | 线程切换打断"读-改-写"复合操作 | `synchronized` / `Lock` / `Atomic*` (CAS) | 互斥（lock/unlock）；CAS 硬件原子指令 |

> **一句话对照：volatile 管可见 + 有序，不管原子；synchronized 三样全管；final 管安全发布的可见性。**

## 第九章：问题汇总

**Q：volatile 能替代 synchronized 吗？**
> 不能。volatile 不保证原子性。只有在"一个线程写、多个线程读"的**纯标志位 / 状态发布**场景下，volatile 才是 synchronized 的轻量替代品。一旦涉及复合操作（`i++`）或多个变量的不变式，必须用锁。

**Q：long / double 有什么特殊？**

> JMM 允许虚拟机把**未被 volatile 修饰的 64 位数据（long/double）的读写**拆成两次 32 位操作，即**非原子性协定**。所以多线程下读写共享的 long/double 可能读到"半个值"（高 32 位来自一次写、低 32 位来自另一次写）。实践中主流 64 位 JVM 都已实现为原子操作，但**语义上仍建议对共享的 long/double 加 volatile**。

**Q：什么是顺序一致性？JMM 保证它吗？**

> 顺序一致性是一个理想模型：多线程程序的执行效果，等同于所有线程的操作按**某种全局顺序**依次执行，且每个线程内部保持原有顺序。
> **JMM 只保证"正确同步的程序"具有顺序一致性。** 未正确同步（共享变量不加 volatile、不用锁）的程序，JMM 不提供任何顺序保证，可能出现各种反直觉结果。

**Q：一句话讲清 JMM！**

> **JMM 是一套围绕"可见性、有序性、原子性"建立的线程通信规范：它把内存抽象成主内存与工作内存，用八大原子操作描述交互，用 happens-before 向程序员承诺可见性与顺序，同时尽可能放开对编译器和 CPU 的重排序限制以换取性能。**

## 附：一页纸记忆卡片

**八大原子操作口诀**
> 锁：lock 清副本，unlock 要写完；
> 读：read-load-use，成对不能断；
> 写：assign-store-write，顺序不能乱；
> volatile：不保原子，可见、禁重排。

**知识地图**

| 维度 | 要点 |
| --- | --- |
| **为什么需要** | 缓存致不可见、重排致无序、切换致非原子 |
| **抽象结构** | 主内存（共享）+ 工作内存（私有副本），通信必经主存 |
| **八大操作** | 读：read→load→use；写：assign→store→write；锁：lock/unlock |
| **重排序** | 三种来源（编译器 / CPU / 内存系统），单线程有 as-if-serial 保底 |
| **核心规则** | happens-before 八条，可传递，不等于时间先后 |
| **volatile** | 可见 + 禁重排（内存屏障），**不保原子** |
| **synchronized** | 原子 + 可见 + 有序，全包；释放-获取 ≡ volatile 写-读 |
| **final** | 写 final 与发布引用不重排；但救不了 this 逃逸 |
