多轮对话记忆设计

发布日期：2026-10-05
RAG 与智能体 多轮对话 Memory 上下文管理 Token Java

多轮对话记忆设计

核心主题：如何在有限 Token 和有限上下文窗口内，让大模型稳定地理解多轮对话、持续推进任务，并正确处理目标变化、约束变化和长期偏好。

本文在原有内容基础上，对章节结构、概念关系、工程流程和落地方法进行了重新整理与补强。核心观点保持不变。

原文章引用地址：https://my.feishu.cn/docx/MiIpdF2XBoaQdox9OOhcob6anOe

1. 为什么需要多轮对话 Memory

做大模型多轮对话时，最容易遇到的工程问题之一就是：

对话越来越长，模型越来越“不稳定”。

一开始，我们很容易采用最直接的方式：

system prompt + 所有历史 messages + 当前用户输入

短对话没有明显问题。

但当用户连续聊几十轮、上百轮以后，就会逐渐出现：

  • Token 成本越来越高
  • 请求和推理延迟增加
  • 上下文逐渐接近甚至超过窗口上限
  • 重要约束被大量无关内容淹没
  • 旧目标和新目标混在一起
  • 已经被用户否定的方案可能重新出现
  • 用户长期偏好和当前临时要求发生混淆
  • 模型需要自己从大量历史中判断“什么还有效”

所以，多轮对话真正需要解决的并不是：

如何保存更多历史消息？

而是：

如何在有限 Token 内，
保留对下一步推理最有价值的信息？

这就是整套设计的核心。

2. 对话历史不等于 Memory

可以先建立一个非常重要的认知：

Conversation History
        ↓
     原始材料
        ↓
筛选 / 提取 / 压缩 / 结构化
        ↓
      Memory
        ↓
服务后续推理与决策

History 是发生过什么，Memory 是未来还需要知道什么。

例如用户说：

用户：我想做一个旅行计划。
用户：先不用生成完整计划。
用户：先比较三个目的地的优缺点。

如果只是保存历史，三个目标都存在。

但真正用于下一次推理的 Memory 应该表达：

{
  "current_goal": "比较三个目的地的优缺点",
  "deprecated_goals": [
    "生成完整旅行计划"
  ]
}

因此，一个真正可用的 Memory 系统，需要同时解决四件事情：

记住什么
更新什么
遗忘什么
什么时候把什么信息送给模型

也就是说：

Memory 不是简单的“存储”，而是一套面向未来推理的信息治理机制。

3. 先看模型边界：长上下文为什么不能解决一切

现在很多模型都支持长上下文，几万 Token、几十万 Token 甚至更长。

于是很容易产生一种想法：

既然上下文窗口足够大，
那就把所有历史都塞进去，
还要 Memory 干什么？

工程上，这个判断并不可靠。

至少需要区分三个概念：

模型能放下多少 Token
        ≠
模型能不能在长文本中找到目标信息
        ≠
模型能不能稳定地把多轮上下文转化成正确决策

例如某个模型支持：

128K context

并不意味着：

128K 中每一条信息都能被同样稳定地利用

更不意味着：

模型一定能正确处理几十轮甚至几百轮的目标变化、
约束变化、方案废弃和状态推进。

3.1 大海捞针和多轮记忆不是一回事

“大海捞针”类能力主要考察：

模型能不能在很长的上下文中找到一条明确存在的信息。

而多轮对话真正困难的是：

模型不仅要找到信息，还必须判断这条信息现在是否仍然有效。

例如：

用户：我想让助手帮我生成一份旅行计划。

用户：算了，先不生成完整计划，先比较几个目的地的优缺点。

模型需要解决的并不是“能不能找到两句话”，而是：

哪个目标是当前目标？
哪个目标已经失效？
下一步到底应该做什么？

因此，更稳定的方式是显式维护状态：

{
  "current_goal": "比较几个目的地的优缺点",
  "deprecated_goals": [
    "生成完整旅行计划"
  ]
}

字段含义

字段 含义 使用要点
current_goal 当前仍然有效的目标 当前执行只应围绕这个目标展开
deprecated_goals 已被用户放弃或覆盖的旧目标 可追溯变化，但不能继续作为执行依据

所以：

长上下文模型可以减少压缩频率，但不能替代上下文治理和 Memory。

4. 多轮对话记忆到底要解决什么问题

从工程角度，可以把问题拆成 6 类。

问题 核心诉求 常见 Memory
最近发生了什么 保持当前语境 Recent Messages
前面讨论过什么 保留历史背景 Summary
现在到底要做什么 保持任务连续性 Task State
哪些事情不能忘 保存硬约束与关键事实 Constraints / Facts
已经决定了什么 避免重复讨论、重复执行 Decisions
用户长期喜欢什么 实现跨会话个性化 User Profile

所以真正成熟的系统，通常不是：

一种 Memory 解决所有问题

而是：

Recent
+ Summary
+ Task State
+ Decisions
+ Facts
+ User Profile

不同 Memory 负责不同生命周期、不同重要程度的信息。

5. 常见上下文处理方案

多轮对话处理不存在“一种方法打天下”。

从简单到复杂，可以分成以下方案：

方案 核心做法 实现成本 Token 成本 信息保真度 主要风险
全量历史 每次把所有 messages 发给模型 低 很高 高 成本高、超窗口、噪音多
滑动窗口 只保留最近 N 轮 低 低 低~中 早期关键约束丢失
固定 Token 截断 按 Token 长度裁剪历史 低 可控 不稳定 可能截断关键内容
摘要 Summary 把旧历史压缩为摘要 中 中低 中 信息损失、摘要漂移
分段 / 递归摘要 分段压缩后再汇总 中高 中 中 错误累积
Task State 将对话转成结构化状态 高 低~中 高 Schema 设计复杂
Decision / Fact Memory 单独保存关键事实和决定 中 低 高 冲突处理复杂
User Profile 保存长期用户偏好 中 低 中高 临时偏好长期化
混合策略 多种 Memory 分层组合 高 可控 高 架构复杂

真实产品里，最常见的是：

recent messages
+ summary
+ task state
+ decisions
+ key facts
+ user profile

而不是只使用其中一种。

6. 全量历史：最简单的 Baseline

最简单的方法：

system prompt + all previous messages + current user input

6.1 优点

  • 实现简单
  • 原始信息保留完整
  • 不需要设计 Memory Schema
  • 便于问题排查和历史追溯

6.2 缺点

  • 对话越长，Token 成本越高
  • 请求延迟不断增加
  • 可能超过上下文窗口
  • 大量无关内容进入模型
  • 旧目标与新目标混在一起
  • 模型需要自己判断哪些信息仍然有效

6.3 适用场景

适合：

  • 非常短的对话
  • 低频内部工具
  • 原型验证
  • 确实要求模型阅读全部原始内容的场景

不适合：

  • 长期会话
  • 用户量大的产品
  • 成本敏感系统
  • 目标和约束频繁变化的复杂任务

可以把它理解为：

最朴素的 Baseline：适合先跑起来，不适合作为长期方案。

7. 滑动窗口：解决“最近语境”

滑动窗口是最容易落地的上下文处理方法。

核心思想：

只保留最近 N 轮消息

或者：

只保留最近 N 个 Token

例如：

最近 5 轮

或者：

最近 3000 Token

7.1 滑动窗口最擅长什么

它最擅长保持局部语境，例如：

用户：这个方案不太好。

助手：你是指摘要压缩那部分吗？

用户：对，就这个。

“这个”的指代，需要依赖最近几轮。

所以滑动窗口适合：

  • 闲聊
  • 简单问答
  • 短任务
  • 当前话题连续性明显的场景
  • 最近信息明显比早期信息重要的场景

7.2 它解决不了什么

假设用户很早之前说：

不要自动提交订单。

但后续聊天很多，这句话最终被滑出窗口。

此时模型可能重新做出错误判断。

所以：

滑动窗口 = 解决局部语境

而不是：

滑动窗口 = 解决长期记忆

8. 固定 Token 截断：底层安全阀

固定 Token 截断比单纯按轮数更加可控。

基本逻辑：

if history_tokens > token_budget:
    从最旧消息开始删除
    直到剩余内容 <= token_budget

优点：

  • 实现简单
  • Token 成本可控
  • 不需要额外调用模型摘要
  • 很适合做底层兜底机制

问题是：

Token 截断理解不了语义。

例如：

用户：以下三个要求必须遵守：

1. 不自动提交订单
2. 必须先让用户确认
3. 金额超过 500 元时需要二次确认

如果截断发生在中间，可能变成：

2. 必须先让用户确认
3. 金额超过 500 元时需要二次确认

或者：

以下三个要求必须遵守：

信息虽然减少了 Token，但语义被破坏。

因此固定截断更适合定位为：

底层安全阀

而不是：

主要 Memory 机制

更稳妥的策略是：

先提取关键约束 / 关键事实 / 当前状态
                ↓
保护这些信息
                ↓
再对普通历史做 Token 截断

9. Summary Memory：保存历史背景

Summary 是最常见的上下文压缩方法。

典型结构：

system instruction
+ conversation summary
+ recent messages
+ current user input

它的价值是：

用更少 Token 保留旧对话的语义背景。

9.1 不要做“流水账摘要”

例如：

用户先问 A，
然后问 B，
之后讨论 C，
最后又补充 D。

看起来很完整，但对后续推理的帮助有限。

模型真正需要的通常不是：

过去发生了什么的完整时间线

而是：

现在应该依据什么继续

9.2 更推荐“状态摘要”

例如：

当前任务：协助用户完成一次售后问题处理。

用户目标：查询订单状态，并判断是否需要申请退款。

业务范围：只处理订单查询、退款规则说明和人工客服转接。

关键约束：不能替用户自动提交退款申请，必须先获得明确确认。

当前进展：已确认订单号，还需要核对退款原因。

这样的 Summary 对后续模型更有价值。

9.3 Summary 适合什么

适合：

  • 长对话背景保留
  • 写作协作
  • 方案讨论
  • 需求澄清
  • 成本敏感但不能完全丢旧背景的场景

不适合单独承担：

  • 精确代码
  • 法律条款
  • 金额、时间、数字等高精度信息
  • 不允许丢失的硬约束
  • 已确认的重要决策

因为 Summary 本质上仍然是：

有损压缩。

10. 递归摘要与分段压缩

当对话极长时，一次摘要可能仍然不够。

可以采用两类方法。

10.1 分段摘要

长历史
  ↓
拆成多个片段
  ↓
每个片段生成局部摘要
  ↓
多个局部摘要
  ↓
合成全局摘要

适合超长历史。

10.2 递归摘要

旧 Summary + 新增 Messages
            ↓
       新 Summary

适合长期持续对话。

例如：

第 1 阶段：
summary_1

第 2 阶段：
summary_1 + 新消息
       ↓
summary_2

第 3 阶段：
summary_2 + 新消息
       ↓
summary_3

10.3 递归摘要最大的风险：摘要漂移

例如原始约束：

不要自动提交退款申请。

第一次摘要：

用户暂时不希望提交退款申请。

第二次摘要：

主要关注退款处理，也可以在合适时机发起申请。

此时约束已经发生变化。

所以：

递归摘要不能把所有信息都压进一个 Summary。

应该把：

可压缩背景

与：

不可漂移信息

分开保存。

例如：

{
  "summary": "用户正在咨询订单售后问题，已提供订单号。",
  "constraints": [
    "不能自动提交退款申请",
    "提交任何售后操作前必须获得用户确认"
  ],
  "decisions": [
    "当前只查询订单状态，不发起退款"
  ]
}

11. Task State：让模型知道“现在做到哪一步”

Task State 是比 Summary 更强的一种 Memory。

它不是把历史压缩成一段自然语言，而是：

把对话转成结构化状态。

例如：

{
  "current_goal": "帮助用户排查订单售后问题",
  "user_intent": "了解订单是否可以退款",
  "task_type": "客服售后处理",
  "scope": {
    "include": [
      "订单状态查询",
      "退款规则说明",
      "退款原因确认",
      "必要时转人工客服"
    ],
    "exclude": [
      "自动提交退款申请",
      "替用户修改订单信息"
    ]
  },
  "constraints": [
    "任何涉及资金或订单变更的操作都必须二次确认",
    "不能承诺系统外无法验证的结果"
  ],
  "current_focus": "确认退款原因和订单状态"
}

11.1 Task State 可以拆成什么

字段 含义 适合保存
current_goal 当前任务目标 当前必须完成的事情
user_intent 用户真实意图 用户想解决什么问题
task_type 当前任务类型 客服、写作、代码、规划、问答等
scope.include 当前任务允许范围 可以做什么
scope.exclude 当前任务排除范围 不应该做什么
constraints 必须遵守的硬约束 安全、权限、业务和用户限制
current_focus 当前推进位置 当前做到哪一步

11.2 Summary 和 Task State 的区别

维度 Summary Task State
表达方式 自然语言 结构化字段
容易模糊 较容易 较少
更新方式 常常整体重写 可以局部更新
冲突处理 不明显 可以显式覆盖
可检查性 较弱 较强
核心作用 背景保留 连续推理和执行

可以把它简单理解成：

summary = 背景材料
task state = 当前任务面板

12. Decision / Fact Memory：保存不能丢的信息

有些信息不能只靠 Summary。

这类信息包括：

  • 已确认目标
  • 关键约束
  • 用户明确否定的范围
  • 已经做出的决策
  • 重要事实
  • 不允许违反的边界

例如：

{
  "decisions": [
    "当前只查询订单状态",
    "暂不提交退款申请",
    "如果订单已发货，需要先说明退货规则"
  ],
  "constraints": [
    "不能自动执行退款",
    "涉及金额变更必须让用户确认"
  ]
}

12.1 Decisions 和 Constraints 的区别

字段 含义 示例
decisions 已经确定的处理结论或阶段性选择 当前只查询订单状态
constraints 后续始终必须遵守的边界 涉及金额变更必须让用户确认

可以进一步理解为：

Constraint：
无论怎么推进，都不能违反。

Decision：
当前已经决定怎么推进。

两者都属于高优先级 Memory。

13. 目标变化：Memory 不能只 Append

多轮对话中，最容易出问题的地方之一就是：

用户会改变想法。

错误设计：

{
  "goals": [
    "生成完整旅行计划",
    "比较目的地优缺点"
  ]
}

这里的问题是：

模型不知道当前到底执行哪个目标。

更合理：

{
  "current_goal": "比较目的地优缺点",
  "deprecated_goals": [
    "生成完整旅行计划"
  ]
}

所以 Memory 更新机制不能简单做：

append

而应该做：

merge

也就是：

旧状态 + 新信息
        ↓
分析关系
        ↓
补充 / 覆盖 / 冲突 / 澄清 / 废弃
        ↓
生成新状态

13.1 常见更新关系

新旧关系 处理方式
补充 添加到对应字段
覆盖 更新当前字段，旧值标记为 deprecated
冲突 按优先级保留最新明确指令
澄清 把模糊字段更新为更具体的表达
废弃 从当前有效状态中移出

例如：

用户：可以直接帮我退了。

用户：等等，先别退，我想先看看退款规则。

正确状态：

{
  "current_decision": "先说明退款规则，不提交退款申请",
  "deprecated_decisions": [
    "直接提交退款申请"
  ]
}

这就是：

决策覆盖，而不是决策并列。

14. User Profile：跨任务长期记忆

User Profile 用来保存：

跨任务、跨会话仍然相对稳定的信息。

例如：

{
  "language": "简体中文",
  "style": "偏工程实践，解释要清楚",
  "background": "关注大模型应用开发",
  "format_preference": "偏好先看简短结论，再看详细说明"
}

14.1 常见字段

字段 含义 更新原则
language 长期语言偏好 多次稳定出现后再写入
style 长期回答风格偏好 不要把单次要求写入长期画像
background 用户背景或专业方向 用于调整解释深度和术语密度
format_preference 常用输出格式偏好 例如表格、步骤、先结论后细节

14.2 最大风险：临时要求长期化

例如：

用户：这次回答简洁一点。

不能直接变成：

{
  "style": "永远简洁"
}

更合理：

当前任务要求
    ↓
Task State

而：

跨多次任务、长期稳定出现
    ↓
User Profile

可以记住一个简单判断：

只对当前任务有效
    → task state

跨任务长期有效
    → user profile

15. Memory 分层：真实系统通常怎么组合

真实系统很少只使用一种 Memory。

一个比较清晰的分层结构：

{
  "recent_messages": [],
  "summary": "",
  "task_state": {},
  "decisions": [],
  "facts": [],
  "user_profile": {}
}

这不要求所有系统字段名完全一样，但表达了核心思想：

不同信息应该有不同的生命周期、优先级和更新方式。

15.1 各层职责

Memory 主要职责 生命周期 不应该承担的职责
Recent Messages 局部语境、指代、语气延续 很短 长期约束
Summary 历史背景压缩 中等 精确事实、关键决策
Task State 当前目标、范围、进展 当前任务 长期用户画像
Decisions 已确认结论 任务内高优先级 普通背景
Facts 关键事实 按业务需要 无关闲聊
User Profile 长期偏好和背景 跨任务 临时要求

可以把它理解成：

Recent
  ↓
解决“刚才发生了什么”

Summary
  ↓
解决“之前大概发生了什么”

Task State
  ↓
解决“现在到底要做什么”

Decision / Fact
  ↓
解决“哪些东西不能搞错”

User Profile
  ↓
解决“这个用户长期有什么偏好”

16. Prompt 组装：不是把所有 Memory 平铺进去

有了 Memory 之后，还要考虑：

到底以什么顺序送给模型？

一个常见、清晰的结构：

System Instruction
        ↓
User Profile
        ↓
Current Task State
        ↓
Constraints / Decisions / Key Facts
        ↓
Summary
        ↓
Recent Messages
        ↓
Current User Input

即：

system instruction
用户长期偏好
当前任务状态
关键约束 / 已确认决策 / 关键事实
摘要背景
最近上下文
当前用户输入

16.1 为什么要分优先级

假设：

长期偏好：回答简洁
当前指令：这次详细展开

应该：

听当前指令

再例如：

summary：
用户准备直接退款。

decision：
当前暂不提交退款申请。

应该：

听 decision

再例如：

recent messages：
模型推测用户可能准备修改订单。

task state：
当前明确禁止修改订单。

应该：

听 task state

因此，推荐一个基础优先级：

当前用户输入
        >
当前任务状态
        >
关键约束 / 已确认决策
        >
用户长期偏好
        >
摘要
        >
最近消息中的隐含推断

注意：

这里强调的是信息冲突时的决策优先级，不是简单地认为越靠前的内容在 Prompt 中一定越强。

17. 如何设计 Memory 更新机制

Memory 系统最核心的动作不是“读”，而是：

Extract
→ Merge
→ Store
→ Retrieve

可以拆成一个标准流程。

17.1 Extract：从当前对话提取变化

输入：

历史 Memory
+
最近对话
+
当前用户输入

输出：

目标变化
约束变化
决策变化
事实变化
偏好变化
进展变化

17.2 Merge：合并新旧状态

例如旧状态：

{
  "current_goal": "生成旅行计划"
}

新消息：

先别生成计划，先比较目的地。

Merge 后：

{
  "current_goal": "比较目的地",
  "deprecated_goals": [
    "生成旅行计划"
  ]
}

17.3 Store：按类型分别保存

不要把所有内容都拼成一个大字符串。

更合理的方式是逻辑分层：

conversation
├── raw_messages
├── summary
├── task_state
├── decisions
├── facts
└── user_profile

底层可以落在数据库、缓存、文档存储等不同介质上，关键不是“必须用什么数据库”，而是：

逻辑上一定要分层。

17.4 Retrieve：只取当前需要的 Memory

不要把所有 Memory 都无脑传给模型。

例如：

当前是简单聊天
→ recent 即可

当前是复杂写作任务
→ summary + task_state + recent

当前是代码调试
→ task_state + decisions + recent + 相关事实

当前是跨会话长期助手
→ user_profile + task_memory + recent

因此 Memory 不只是：

怎么存

还包括：

怎么取

18. 如何设计压缩 Prompt

压缩 Prompt 的目标不应该是：

请把历史总结一下。

这种 Prompt 很容易生成流水账。

更好的方式是：

你是一个对话状态压缩器。

请从当前对话中提取对后续任务有用的信息。
不要写流水账。
不要保留寒暄、重复表达、失败尝试和已经废弃的目标。

重点提取：
- 当前目标
- 任务范围
- 约束条件
- 已做决策
- 用户偏好
- 未解决问题
- 当前进展

如果目标发生变化，请覆盖旧目标。
如果旧目标已经失效，请放入 deprecated_goals。
如果存在明确约束，请放入 constraints，
不要只写在 summary 中。

推荐结构化输出：

{
  "summary": "",
  "current_goal": "",
  "scope": {
    "include": [],
    "exclude": []
  },
  "constraints": [],
  "decisions": [],
  "preferences": [],
  "open_questions": [],
  "progress": [],
  "deprecated_goals": []
}

18.1 字段职责

字段 含义 提取建议
summary 旧对话背景 只保留后续有用背景
current_goal 当前目标 用户改目标时覆盖
scope.include 任务包含范围 明确应该处理什么
scope.exclude 任务排除范围 明确不应该处理什么
constraints 约束 明确要求和业务边界
decisions 已确认决策 保存已经定下来的方向
preferences 偏好 注意区分当前偏好和长期偏好
open_questions 未解决问题 保存后续待确认事项
progress 当前进展 记录已完成和下一步
deprecated_goals 废弃目标 防止模型重新执行旧目标

19. 如何防止 Summary 漂移

Summary 漂移指：

多次压缩后，重要信息逐渐丢失、变形或弱化。

例如：

原始信息
↓
summary_1
↓
summary_2
↓
summary_3
↓
summary_n

每次都是有损压缩。

19.1 核心方案：拆分“可压缩”和“不可漂移”

例如：

{
  "summary": "",
  "state": {},
  "constraints": [],
  "decisions": []
}

其中：

字段 是否允许有损压缩 说明
summary 可以 背景允许概括
state 不建议随意有损 结构化表示当前状态
constraints 不允许 漂移可能导致行为越界
decisions 不允许 漂移可能导致回到旧方案

核心原则：

summary 可以有损压缩
constraints 不允许漂移
decisions 不允许漂移
state 必须可更新、可检查

19.2 给关键 Memory 保留来源

更稳妥的工程做法是：

{
  "constraint": "不能自动提交退款申请",
  "source": "message_182",
  "status": "active"
}

这样出现问题时可以追溯：

这条 Memory 是从哪条用户消息提取的？

即便后续 Summary 出错，也可以回看原始消息。

因此成熟系统最好保留：

Memory + 来源 + 状态 + 更新时间

20. 哪些信息应该被遗忘

好的上下文系统不只是会记：

还必须会忘。

应该弱化或遗忘的信息包括：

  • 寒暄
  • 重复表达
  • 已废弃目标
  • 无用中间推理
  • 失败尝试
  • 低置信度猜测
  • 与当前任务无关的闲聊
  • 一次性偏好

例如：

用户：我刚吃完饭，我们继续。

除非当前任务和饮食有关，否则没有必要进入长期 Memory。

再例如：

用户：先生成完整旅行计划。

用户：算了，先别生成计划，
先比较几个目的地。

正确做法不是把两个目标永久并列保存，而是：

current_goal
    ↓
比较目的地

deprecated_goals
    ↓
生成完整旅行计划

21. 一个更完整的 Memory 生命周期

如果从整个系统生命周期来看，可以把 Memory 理解为：

Raw Message
     ↓
   Extract
     ↓
   Normalize
     ↓
   Merge
     ↓
   Validate
     ↓
   Store
     ↓
 Retrieve
     ↓
Prompt Assemble
     ↓
     LLM
     ↓
执行结果 / 新消息
     ↓
再次 Extract

其中最关键的是：

Extract
Merge
Validate
Retrieve

21.1 Validate：不要完全信任 Memory 提取结果

Memory 本质上可能来自模型生成，因此应该允许校验。

例如：

旧约束：
不能自动退款。

新提取：
可以自动退款。

这时不能简单覆盖。

应该进入：

冲突检测
    ↓
检查来源
    ↓
判断是不是用户明确修改
    ↓
确定是否真的需要覆盖

因此：

“Memory 是结构化的”不代表“Memory 一定正确”。

结构化只是让它更容易检查、更新和控制。

22. 整体工程架构

一个完整的上下文处理系统，可以设计为：

                 ┌──────────────────┐
                 │   Raw Messages   │
                 └────────┬─────────┘
                          ↓
                 ┌──────────────────┐
                 │  Context Policy  │
                 └────────┬─────────┘
                          ↓
                 ┌──────────────────┐
                 │ Memory Extractor │
                 └────────┬─────────┘
                          ↓
                 ┌──────────────────┐
                 │  Memory Merger   │
                 └────────┬─────────┘
                          ↓
                 ┌──────────────────┐
                 │ Memory Validator │
                 └────────┬─────────┘
                          ↓
                 ┌──────────────────┐
                 │   Memory Store   │
                 └────────┬─────────┘
                          ↓
                 ┌──────────────────┐
                 │ Prompt Assembler │
                 └────────┬─────────┘
                          ↓
                    ┌───────────┐
                    │    LLM    │
                    └───────────┘

22.1 各模块职责

模块 职责
Raw Messages 保存完整原始对话，便于追溯
Context Policy 决定本次采用什么上下文策略
Memory Extractor 提取目标、约束、决策、事实、偏好、进展
Memory Merger 处理补充、覆盖、冲突和废弃
Memory Validator 检查重要 Memory 是否出现异常变化
Memory Store 分层保存各种 Memory
Prompt Assembler 根据优先级和 Token 预算组装 Prompt
LLM 基于当前输入和治理后的上下文进行推理

23. Context Policy：不要每次都使用相同策略

真正的工程系统最好不要简单写死：

永远最近 10 轮

或者：

永远 Summary + Recent

更合理的是：

根据任务动态选择上下文策略

例如：

短闲聊
→ recent

普通多轮任务
→ recent + summary

复杂任务
→ recent + summary + task_state

高风险任务
→ recent + task_state + constraints + decisions + key facts

跨会话长期助手
→ user_profile + task memory + recent

因此可以把 Context Policy 理解成：

本次请求到底应该把哪些 Memory 送给模型。

24. 不同场景应该选什么方案

场景 推荐方案 原因 不推荐
闲聊 滑动窗口 最近语境最重要 复杂 Task State
简单问答 最近 N 轮或单轮 历史价值低 长摘要链
短任务 滑动窗口 + 少量约束 成本低 全量长期历史
写作协作 Summary + Task State + Recent 要保留主题、风格、进展 只用滑动窗口
代码任务 Task State + Decisions + Recent 需要保持文件、错误、决策和当前步骤 只用自然语言 Summary
方案设计 Summary + Task State + Decisions 需求会反复变化 全量历史堆叠
客服 Summary + Facts + Recent 需要保持问题、订单和处理状态 只保留最近几轮
Agent Task State + Tool State + Decisions 多步骤执行状态必须可控 只用 Summary
长期助手 User Profile + Task Memory + Recent 需要跨会话个性化 把所有偏好混入 Summary

可以总结：

任务越短
→ 越可以依赖 Recent

任务越长
→ 越需要 Summary

目标越明确
→ 越适合 Task State

约束越重要
→ 越需要 Decisions / Facts

用户关系越长期
→ 越需要 User Profile

25. 不同模型能力下的策略调整

上下文策略也与模型能力有关。

模型类型 典型特点 推荐策略
小模型 成本低、速度快，但长上下文理解能力相对弱 少给原始历史，多给结构化 State、约束和短 Recent
中等模型 能处理一定上下文，但复杂冲突可能不稳定 Recent + Summary + Task State
大模型 推理能力更强，可阅读更多背景 可保留更多原文，但关键状态仍应显式化
长上下文大模型 能承载更多原文 减少压缩频率，但仍然保留 Memory 分层

核心原则：

模型越弱
→ 越需要结构化

上下文越长
→ 越需要治理

任务越复杂
→ 越不能只靠 Recent Messages

26. Token Budget：Context 不是越多越好

工程上还应该考虑一个问题：

本次请求到底给 Context 分配多少 Token？

可以把一次请求粗略看成：

Context Budget
=
System
+
User Profile
+
Task State
+
Constraints / Decisions
+
Summary
+
Recent
+
Current User Input
+
Response Reserve

真正可控的设计，不是：

能塞多少就塞多少

而是：

先保护高价值信息，
再把剩余预算分配给低优先级信息。

例如可以采用：

第一优先级：
当前输入 + 硬约束 + 当前状态

第二优先级：
已确认决策 + 关键事实

第三优先级：
Summary

第四优先级：
Recent 中较旧的部分

当 Token 不够时：

先减少低优先级内容
不要首先牺牲高优先级 Memory

27. Memory 与原始消息应该分离

一个成熟系统不要因为 Memory 已经提取出来了，就删除原始消息。

推荐：

Raw Messages
    ↓
永久 / 长期保存

同时：

Raw Messages
    ↓
提取
    ↓
Memory Store

即：

原始事实源
+
加工后的 Memory

两套信息各自承担不同职责。

Raw Messages

负责：

  • 追溯
  • 审计
  • Debug
  • Memory 修复
  • 重新摘要
  • 重新构建状态

Memory

负责：

  • 快速推理
  • 低 Token 上下文
  • 状态管理
  • 个性化
  • 任务连续性

所以不要把 Memory 当成：

原始历史的唯一备份

更准确的关系是：

Raw Message = Source of Truth

Memory = 面向推理的派生状态

28. 记忆冲突处理

多轮系统中经常会出现：

旧信息 A
+
新信息 B

而 A 与 B 不一致。

常见情况：

目标覆盖
偏好修改
约束新增
约束解除
决策撤销
事实更正

推荐处理方式不是：

全部并列保存

而是：

识别关系
    ↓
判断优先级
    ↓
更新 Current State
    ↓
旧值进入历史 / deprecated

例如：

{
  "current_goal": "比较目的地优缺点",
  "deprecated_goals": [
    "生成完整旅行计划"
  ]
}

或者：

{
  "current_decision": "暂不退款",
  "deprecated_decisions": [
    "直接提交退款"
  ]
}

这种设计的价值在于：

让模型看到“当前有效状态”，而不是一堆未经治理的历史记录。

29. 一个完整的多轮对话例子

假设用户在进行一个复杂售后任务。

第 1 轮

用户：
帮我看看订单能不能退款。

初始：

{
  "current_goal": "判断订单是否可以退款",
  "task_type": "售后",
  "current_focus": "收集订单信息"
}

第 2 轮

用户：
订单号是 A10086。

Memory：

{
  "facts": [
    {
      "key": "order_id",
      "value": "A10086"
    }
  ]
}

第 3 轮

用户：
如果可以退款，你直接帮我退，不用再问我。

如果系统允许直接执行，可能形成：

{
  "decision": "用户授权满足条件时提交退款",
  "constraints": []
}

但如果业务规则要求资金类操作必须确认，则应由系统规则拦截，而不能只依据 Memory。

这说明：

Memory 是上下文管理机制，不应该取代业务权限和安全规则。

第 4 轮

用户：
等等，先别退，我想先看看退款规则。

状态更新：

{
  "current_goal": "先说明退款规则",
  "decisions": [
    "当前只查询和解释退款规则"
  ],
  "deprecated_decisions": [
    "直接提交退款申请"
  ]
}

下一轮模型就不会再次直接执行原来的目标。

30. Memory 设计中的几个核心原则

可以把前面的内容压缩成以下原则。

30.1 History 和 Memory 分离

History = 原始事实
Memory = 推理状态

30.2 Summary 和 State 分离

Summary = 背景
State = 当前状态

30.3 Background 和 Constraint 分离

Summary 可以损失
Constraint 不能漂移

30.4 Current 和 Deprecated 分离

当前有效状态
+
已经废弃的历史状态

30.5 Current Task 和 Long-term Profile 分离

Task State = 当前任务
User Profile = 长期用户

30.6 Append 不等于 Memory Update

真正的更新应该是：

merge

而不是：

append

30.7 Retrieval 和 Storage 同样重要

存得再完整，如果取错信息，模型一样会答错。

31. 如何评估上下文处理效果

上下文处理不能只看：

压缩了多少 Token

真正重要的是：

压缩之后，模型还能不能继续正确完成任务。

可以从以下维度评估。

维度 含义 示例
Recall 关键约束是否还记得 “不能自动提交订单”是否保留
Precision 是否记入了不该记的内容 “我刚吃饭了”是否进入长期 Memory
Freshness 是否使用最新目标 是否还执行已废弃的旧目标
Consistency Memory 之间是否一致 Summary 和 State 是否冲突
Compression Ratio 压缩效率 用更少 Token 保留多少核心信息
Recovery 任务恢复能力 跨会话后能否继续工作
Robustness 抗干扰能力 插入闲聊后是否仍遵守硬约束

31.1 建议设计的测试问题

每一次 Memory 方案升级后，可以反复测试：

1. 当前目标是否清楚？
2. 关键约束是否还在？
3. 旧目标是否已经废弃？
4. 模型是否使用最新指令？
5. 无关信息是否被过滤？
6. 摘要与状态是否一致？
7. 压缩后是否还能恢复任务？

如果这些问题经常回答不清楚，说明系统只是：

裁剪历史

而不是：

真正设计 Memory

32. 推荐的整体落地方案

如果从“工程上既稳定又不过度复杂”的角度出发，可以采用下面这套组合：

                    用户输入
                       ↓
                ┌───────────────┐
                │ Raw Messages  │
                └───────┬───────┘
                        ↓
               Memory Extractor
                        ↓
                ┌───────────────┐
                │ Merge / Update│
                └───────┬───────┘
                        ↓
        ┌───────────────┼─────────────────┐
        ↓               ↓                 ↓
   Task State        Summary        Decisions / Facts
        │               │                 │
        └───────────────┼─────────────────┘
                        ↓
                 Context Policy
                        ↓
                Prompt Assembler
                        ↓
                       LLM

长期用户信息再独立为：

32.1 推荐的默认 Context

对于一个普通的复杂多轮任务，可以优先使用：

system instruction
+
user profile（需要时）
+
task state
+
constraints
+
decisions
+
key facts
+
summary
+
recent messages
+
current input

这套组合可以覆盖：

最近语境
+
历史背景
+
当前目标
+
关键约束
+
已确认决策
+
关键事实
+
长期偏好

同时又避免把所有原始消息全部塞入模型。

33. 最终总结

多轮对话中的上下文处理，不是一个单一技术点，而是一套信息治理策略。

全量历史
→ 最简单，但成本高、稳定性差

滑动窗口
→ 解决最近语境

固定 Token 截断
→ 控制上下文长度，是底层安全阀

Summary
→ 保留历史背景

递归 / 分段摘要
→ 应对超长历史，但需要防止漂移

Task State
→ 保存当前任务状态

Decisions / Facts
→ 保护关键决策与不可丢事实

User Profile
→ 支持跨任务、跨会话个性化

Hybrid Memory
→ 真正产品中的主流思路

最终可以用几句话记住整套设计。

对话历史不是记忆，
记忆是为未来决策服务的信息结构。

上下文窗口长度，
不等于上下文理解能力。

大海捞针能力，
不等于多轮状态管理能力。

Summary 用于背景，
State 用于推理。

Recent 解决局部语境，
Structured Memory 解决任务连续性。

Memory 更新不是简单 append，
而应该是 merge。

好的 Memory 系统 =
会记住
+
会更新
+
会遗忘
+
会处理冲突
+
会按场景选择策略

真正成熟的超长上下文处理，不是盲目扩大上下文窗口，也不是简单压缩历史，而是：

根据任务
+ 模型能力
+ Token 成本
+ 信息重要性
+ 业务风险

选择合适的记忆分层、更新、压缩和检索策略。

最终目标只有一个：

让模型在更少 Token 下，仍然拥有足够准确、稳定、连续的“有效上下文”。
